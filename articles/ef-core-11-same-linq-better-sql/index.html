Same LINQ, Better SQL: Inside EF Core 11

How EF Core 11 improves SQL generation behind existing LINQ—and how to verify the effect on a real endpoint.

By Islam Darawsheh October 14, 2026 9 min read

An EF Core upgrade can improve a query without changing its LINQ. In EF Core 11, that can mean fewer repeated joins, fewer sorting columns, and fewer redundant casts.

For a busy endpoint, those changes are worth inspecting. This article explains three improvements to SQL generation and a practical way to check their effect on your application.

Version context: .NET 11 RC2 was announced on October 13, 2026. EF Core 11 is still a prerelease at the time of writing and requires .NET 11. The improvements discussed here belong to the EF11 release cycle; the RC2 announcement provides the current version context. [1] [2]

The C# snippets below assume an existing model and configured context. The SQL examples use SQL Server syntax and illustrate documented changes in an orders domain. They are adapted examples, not captured output from a test run for this article. The actual commands depend on your model, provider, and exact package version.

1. Split queries can stop repeating reference joins

Consider an order with an optional customer and a collection of lines. Assume Order.CustomerId is a nullable foreign key to the customer primary key, and that this example has no global query filters:

var orders = await db.Orders
    .Include(order => order.Customer)
    .Include(order => order.Lines)
    .AsSplitQuery()
    .ToListAsync(cancellationToken);

Customer is a reference navigation: each order points to at most one customer. Lines is a collection navigation: one order can have many lines.

With a split query, EF loads the orders and customer data in one command, and the lines in another. Earlier versions could repeat reference joins in the collection command, even when that command did not need the reference data. The original issue includes examples where adding more reference navigations made this repetition grow. [3]

For an optional customer, a collection command could have this shape:

-- Earlier SQL shape: loading order lines
SELECT line.Id, line.OrderId, line.Quantity,
       ord.Id, customer.Id
FROM Orders AS ord
LEFT JOIN Customers AS customer ON ord.CustomerId = customer.Id
INNER JOIN OrderLines AS line ON ord.Id = line.OrderId
ORDER BY ord.Id, customer.Id;

EF11 can recognize an unnecessary to-one join and prune it:

-- EF11 SQL shape: the collection command needs no customer data
SELECT line.Id, line.OrderId, line.Quantity, ord.Id
FROM Orders AS ord
INNER JOIN OrderLines AS line ON ord.Id = line.OrderId
ORDER BY ord.Id;

Customer data still comes from the first command. The optimization removes repeated work from a later command; it preserves the requested object graph. The implementation also avoids propagating unnecessary reference identifiers into the query. [4]

The potential benefit is easiest to investigate on an endpoint that combines collections with several reference includes. Look at each executed command and ask which relationships it genuinely needs.

A join remains when its data or filtering effect is needed. Pruning depends on EF proving that removal preserves the result. The merged implementation also handles certain INNER JOINs when the model guarantees a matching row through a required foreign key. It does not remove arbitrary joins. [4]

Inspect your actual commands, especially when relationships or query filters differ from this example.

2. Single queries can use fewer sorting columns

The same improvement also affects single queries. EF11 can omit redundant reference keys from the ordering used to assemble related entities. [2] [4]

Consider the corresponding single-query version with the same reference and collection includes. In a simple shape, the relevant ordering can change as follows; more complex collection graphs can require additional keys:

-- Earlier ordering fragment
ORDER BY ord.Id, customer.Id;

-- EF11 ordering fragment for the corresponding shape
ORDER BY ord.Id;

For a given order, the customer key does not distinguish additional order rows. It is determined by that order's customer relationship.

This does not mean EF removes your business ordering. An explicit ordering by order date, customer name, or another meaningful field remains part of the query's semantics. The change concerns redundant identifiers EF added for materialization.

The performance implication is that this can reduce sorting work when the resulting database plan benefits from a narrower sort key. It does not guarantee that a physical Sort operator disappears: an index might already satisfy the ordering, or other parts of the query may still require sorting.

Review the execution plan alongside the SQL text. A shorter ORDER BY is a useful clue; CPU, memory grants, spills, and elapsed time tell you whether it mattered.

3. EF can remove casts that convert a value to its existing SQL type

EF11 also strips conversions whose target store type matches the operand's store type. The implementation PR demonstrates how an implicit CLR conversion on a value-converted property can introduce such a SQL CAST. [5] [11]

For example, if Reference is already mapped to nvarchar(max), an earlier predicate could have this shape:

WHERE CAST(ord.Reference AS nvarchar(max)) LIKE N'INV-%'

The corresponding cleaned-up predicate is:

WHERE ord.Reference LIKE N'INV-%'

The nvarchar(max) mapping reflects the documented example. For a searchable identifier, choose an appropriate column length and indexing strategy for your application.

The rule is narrow: remove a conversion that does not change the store type. A conversion between genuinely different types can still be necessary.

Removing a wrapper may give the database a better opportunity to optimize the predicate. Whether that changes index use depends on the actual column mapping, indexes, provider, and plan. Do not infer an index seek just because the CAST disappeared.

For an application that uses value objects such as an invoice reference or customer code, this is a good reason to compare generated predicates during an upgrade.

What the published benchmark actually shows

On April 12, 2026, EF developer Shay Rojansky posted a benchmark using SQL Server, 50,000 blogs, three posts per blog, and 100,000 reference entities. It varied the depth of optional reference chains and used a covering index for the posts query. The queries materialized results with AsNoTracking(). Selected timings were: [3]

Query Included reference depth Before After Elapsed time reduction
Split 1 750 ms 530 ms About 29%
Split 3 1,368 ms 1,125 ms About 18%
Single 5 4,051 ms 3,146 ms About 22%

The supplied benchmark code compares the EF implementation with the relevant optimization present versus reverted. These are author-reported results for that setup, not measurements taken for this article or a general EF10-versus-EF11 comparison. [3]

The final column is the percentage reduction in elapsed time, calculated as (before - after) / before × 100.

Use them as evidence that the changes can matter. An API's result also depends on database latency, the data returned, materialization, and the rest of the request. A reduction in query duration does not translate directly into the same reduction in endpoint latency.

Verify the effect on one real endpoint

Start with an endpoint you already care about: perhaps an order details page or an invoice list. Keep its LINQ unchanged for the initial comparison.

Capture every command

ToQueryString() is useful for an initial inspection:

var query = db.Orders
    .Include(order => order.Customer)
    .Include(order => order.Lines)
    .AsSplitQuery();

Console.WriteLine(query.ToQueryString());

Its output is intended for debugging. For split queries, capture the commands during execution so you can review the whole operation. [6]

For a local diagnostic run, filter logging to database commands:

optionsBuilder.LogTo(
    message => Console.WriteLine(message),
    new[] { DbLoggerCategory.Database.Command.Name },
    LogLevel.Information);

This uses Microsoft.EntityFrameworkCore and Microsoft.Extensions.Logging. Configure it where you build the context options, execute the query, and collect the command output. [7]

Keep the comparison controlled

First establish whether the SQL changed, then measure whether the complete operation improved.

Use the same database snapshot, parameters, indexes, tracking behavior, and loading strategy. Record the EF, provider, database, and .NET versions. If changing the runtime alongside EF, report the result as an upgrade comparison rather than attributing all improvement to query translation.

Warm up the application before measuring repeated steady-state runs. Measure first-request behavior separately if that matters to your product. Disable verbose console logging during timing: writing every command to the terminal adds its own cost.

For a useful comparison, collect:

  • Executed SQL and command count.
  • Database logical reads, CPU time, and actual execution plans.
  • Total query duration, including result materialization.
  • Endpoint latency under representative concurrency.
  • Returned root IDs and related data, to confirm equivalent results.

Microsoft's performance diagnosis guidance describes command logging, query plans, and benchmarking as complementary tools. Each answers a different question. [8]

Split queries still have tradeoffs

Cleaner collection commands do not make AsSplitQuery() the best choice for every endpoint. Split queries execute multiple commands, introduce round trips, and can observe inconsistent data if changes occur between those commands. Where supported by your database, a snapshot or serializable transaction can address these consistency requirements, with its own cost. [9]

Benchmark the loading strategy with realistic database latency. A local database can hide the cost of extra trips that becomes obvious after deployment.

Also check whether you need the whole entity graph. A read endpoint that only displays an order number, customer name, and total may benefit more from a focused projection. Efficient query design still includes choosing the needed columns, limiting results, and using appropriate indexes. [10]

An upgrade worth inspecting

EF Core 11 makes a useful kind of improvement: it can reduce database work behind code that already expresses the right intent.

Pick one important query and save its SQL before upgrading. Compare it afterward, inspect the plan, and verify the returned data. Where redundant work disappears and measurements improve, you have a concrete reason to value the upgrade—and a result you can explain to your team.
