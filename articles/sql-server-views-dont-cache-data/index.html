SQL Server Views Don't Cache Data — So When Are They Actually Faster?

Regular views, indexed views, and computed columns: what SQL Server actually stores, what the optimizer can rewrite, and how to test parsing-heavy queries.

By Islam Darawsheh November 17, 2026 13 min read

A question worth asking before creating your next SQL Server view is deceptively simple:

If a view doesn't cache query results, why should I use one? Couldn't I execute the SQL directly from my .NET application, with the exact filters I need, and get a faster result?

The question exposes a common architectural misconception. A regular SQL Server view is not a performance feature by itself. But it isn't necessarily a performance penalty either. And once an application repeatedly parses a delimited NVARCHAR field, the more interesting optimization might be neither a regular view nor an indexed view: it might be an indexed computed column.

Let's separate abstraction, materialization, indexing, and actual query performance.

1. What a regular view actually does

Consider a table and a view that exposes a friendlier projection:

CREATE VIEW dbo.vActiveOrders
AS
SELECT OrderId, CustomerId, OrderDate
FROM dbo.Orders
WHERE IsActive = 1;
GO

SELECT OrderId, OrderDate
FROM dbo.vActiveOrders
WHERE CustomerId = 42;

The view stores its definition, not a stored copy of matching rows. When queried, SQL Server's optimizer can expand the view, combine its logic with the outer query, and consider appropriate access paths on the underlying tables. The equivalent direct query may produce the same execution plan:

SELECT OrderId, OrderDate
FROM dbo.Orders
WHERE IsActive = 1
  AND CustomerId = 42;

There is no requirement for SQL Server to first load every active order and then filter by customer. The optimizer can push eligible predicates down and choose an index seek when a suitable index and cost estimate justify it.

Important qualification: This is an opportunity, not a guarantee. Query shape matters. TOP, aggregation, window functions, DISTINCT, complex nesting, and other constructs can restrict which transformations are valid. Check the actual execution plan rather than assuming SQL Server will always rewrite a query as you imagined.

So why use a regular view? For a stable database contract, reused joins/business definitions, controlled column exposure, and maintainability. Those are legitimate architectural reasons—just don't describe them as automatic caching.

What about SQL Server's caches?

Three different concepts often get confused:

  • Buffer pool: retains frequently accessed data and index pages in memory. Subsequent queries may avoid physical disk reads, whether they query a table or a view.
  • Execution-plan cache: may reuse compiled query plans. Reusing a plan is not reusing its previous result set.
  • Indexed view: physically maintains the view's result in an index. This is materialization, not a time-limited application cache.

If a regular view returns old-looking data, investigate transaction isolation, replicas, application caching, or other layers; the view itself is not a stored snapshot.

3. Indexed views: actual materialization, with a cost

An indexed view begins life as a view created with WITH SCHEMABINDING. It becomes physically materialized when you create its first unique clustered index. You can then add nonclustered indexes.

-- Requires dbo.Documents(DocumentId bigint NOT NULL, CompositeValue nvarchar(100) NOT NULL)
-- and the documented required SET options; see the reproducible script.
CREATE VIEW dbo.vDocumentParts
WITH SCHEMABINDING
AS
SELECT
    DocumentId,
    LEFT(CompositeValue, CHARINDEX(N'|', CompositeValue) - 1) AS Code,
    SUBSTRING(CompositeValue, CHARINDEX(N'|', CompositeValue) + 1, 100) AS Status
FROM dbo.Documents;
GO

CREATE UNIQUE CLUSTERED INDEX CIX_vDocumentParts
    ON dbo.vDocumentParts (DocumentId);
GO

CREATE NONCLUSTERED INDEX IX_vDocumentParts_Code
    ON dbo.vDocumentParts (Code)
    INCLUDE (Status);
GO

This deliberately simple example assumes exactly one delimiter, with nonempty parts. Validate or constrain input data before adopting expressions that subtract one from CHARINDEX.

Queries can explicitly target the stored view:

SELECT DocumentId, Code, Status
FROM dbo.vDocumentParts WITH (NOEXPAND)
WHERE Code = N'ABC';

NOEXPAND tells SQL Server to consider the indexed view as a materialized access path rather than expand it into base-table logic. It does not guarantee an index seek; index choice still depends on the optimizer. INDEX(...) adds stronger hints but should not be a default tuning strategy.

Edition changes the story

For SQL Server 2025, Microsoft documents the following behavior:

CapabilityEnterpriseStandardExpress
Create indexed viewsYesYesYes
Query indexed viewsYesYes, with NOEXPANDYes, with NOEXPAND
Automatic indexed-view matching/substitutionYesNoNo

This matters even when the T-SQL looks identical. SQL Server 2025 also provides Enterprise Developer and Standard Developer editions for development/testing, allowing edition-aware experiments without production licenses.

The price of materialization

When an underlying row changes, SQL Server must maintain the relevant indexed-view rows and indexes as part of the data modification. That adds index storage, transaction-log activity, and potential INSERT/UPDATE/DELETE cost. SCHEMABINDING also constrains schema changes, and eligible indexed-view definitions must meet strict rules: deterministic expressions, correct ownership, supported constructs, and particular session SET options.

Microsoft highlights large aggregations as a common strong use case. Materializing a simple two-part string projection can work, but it is not automatically the best design.

4. The more interesting case: splitting an NVARCHAR column

Imagine a legacy integration that stores two independent values in one field:

DocumentIdCompositeValue
1ABC|ACTIVE
2XYZ|ARCHIVED
3ABC|PENDING

We need Code and Status as separate queryable values. Assume the separator format is consistent.

A regular view is easy:

CREATE VIEW dbo.vParsedDocuments
AS
SELECT
    DocumentId,
    LEFT(CompositeValue, CHARINDEX(N'|', CompositeValue) - 1) AS Code,
    SUBSTRING(CompositeValue, CHARINDEX(N'|', CompositeValue) + 1, 100) AS Status
FROM dbo.Documents;
GO

It centralizes the parsing rule, but it does not store the parsed values. A query such as WHERE Code = N'ABC' may need to evaluate an expression over many candidate rows if there is no useful indexed access path.

Alternative A: a nonpersisted computed column

ALTER TABLE dbo.Documents
ADD Code AS
    LEFT(CompositeValue, CHARINDEX(N'|', CompositeValue) - 1);
GO

This exposes the parsed value on the table without physically storing the computed column in the base row. By itself, that is not a magic speed boost. However, a deterministic, precise, indexable computed column can often be indexed without PERSISTED:

CREATE INDEX IX_Documents_Code
    ON dbo.Documents (Code);
GO

Now a predicate on Code has a potential indexed access path. The index physically stores its key values even though the computed column is nonpersisted in the base row. That distinction is frequently missed.

Alternative B: a persisted computed column

-- Alternative design: run on a separate equivalent table,
-- not on the table already carrying the previous Code column.
ALTER TABLE dbo.Documents
ADD Code AS
    LEFT(CompositeValue, CHARINDEX(N'|', CompositeValue) - 1)
    PERSISTED;
GO

CREATE INDEX IX_Documents_Code
    ON dbo.Documents (Code);
GO

Here SQL Server stores the computed value in the base row and maintains it on changes. You may also index it, but persisting and indexing are separate choices. Persistence can reduce recalculation costs for some read patterns and is necessary for certain otherwise-indexable scenarios; it also increases base-row storage and write maintenance. The fastest choice must be measured under the actual workload.

A likely practical conclusion—not a benchmark result: If your task is to filter frequently on a parsed, row-local value, a properly designed indexed computed column often deserves testing before an indexed view. If you primarily fetch a handful of records by primary key, parsing on demand may already be inexpensive.

Why not simply use STRING_SPLIT?

STRING_SPLIT returns rows, not fixed Code and Status columns. SQL Server 2022 added enable_ordinal = 1, which reports positions, but the returned row order still requires an explicit ORDER BY if order matters. Moreover, indexed-view definitions do not allow table-valued functions or CROSS APPLY/OUTER APPLY. It isn't a drop-in replacement for a deterministic scalar expression inside this indexed view.

If the source data is actually JSON, use the appropriate JSON features instead of pretending it is a pipe-delimited format. If you control the schema, the first question should be whether Code and Status ought to be real columns at all.

5. Does EF Core change the answer?

No. A well-composed EF Core query and a direct T-SQL statement are ultimately optimized by SQL Server. The key is where filtering happens.

// Good: filtering and projection are translated to SQL.
var docs = await db.Documents
    .Where(d => d.DocumentId == requestedId)
    .Select(d => new { d.DocumentId, d.CompositeValue })
    .ToListAsync();

// Bad for large sets: everything is fetched before filtering.
var all = await db.Documents.ToListAsync();
var docsInMemory = all.Where(d => d.DocumentId == requestedId).ToList();

A mapped view can also be queried with additional Where clauses, and EF Core can compose them into SQL when the mapping and query are translatable. Filtering in the application after materialization is not an argument against views; it is usually a data-access mistake.

An ORM does not make expensive string expressions disappear, either. If the bottleneck is repeatedly computing a parsed key for a wide range of rows, solve that database access problem, not merely the location of the SQL string.

The measurements should cover four distinct query shapes: primary-key lookup, selective filtering by parsed Code, low-selectivity filtering by Status, and a broad scan that projects the parsed values. Then test inserts, updates to CompositeValue, and deletes. Each optimization has a different likely winner depending on selectivity and write pressure.

Record logical reads, CPU time, elapsed time, actual execution plan, output row count, and index/storage footprint. Repeat runs after warm-up, compare medians rather than single executions, and avoid clearing shared-server caches. Separately run the SQL Server 2025 and SQL Server 2022 engines; changing only compatibility level is not a true engine comparison.

7. Decision framework: when should you use which?

  • Use a regular view when you need a reusable, stable abstraction over otherwise efficient queries. Don't expect materialization.
  • Use an indexed view when measurements show the stored result is valuable enough to offset write, storage, and schema-maintenance costs—especially for suitable repeated aggregations.
  • Use a computed column when one row's derived value deserves a name and a consistent definition.
  • Index a computed column when queries repeatedly filter or join on its deterministic, indexable result. Do not assume PERSISTED is mandatory.
  • Consider PERSISTED when storing the derived value in the base row benefits your access patterns, or when index eligibility requires it.
  • Use native relational columns when you can redesign the schema and the components are genuinely independent values. A faster workaround for an avoidable parsing problem is still a workaround.

Conclusion: optimize the work, not the abstraction

A regular SQL Server view isn't a cache. Its value is the contract it provides. An indexed view is materialized data with ongoing maintenance costs. A computed column lets SQL Server understand a row-local expression—and indexing it may be the missing performance feature.

The productive question isn't “Are views faster than queries?” It is:

What work does this query repeatedly perform, which access path can eliminate that work, and what will it cost every time the data changes?

That is a question worth answering with an execution plan and a repeatable experiment, not a rule of thumb.
