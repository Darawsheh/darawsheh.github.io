Beyond the Prompt: Engineering AI Agents for Production

A practical architecture for agents that process real requests: defined authority, durable state, safe recovery, and evidence that the work happened.

By Islam Darawsheh September 24, 2026 11 min read

An employee asks an AI agent to submit an equipment request. The agent understands the message, finds the right form, and calls the submission API. The API saves the request, but its response never reaches the agent.

The agent tries again.

Now there are two requests, and the employee receives a confident message saying everything is done.

This is a hypothetical example, but it exposes a useful engineering question: what should the application do when the model understands the task and execution still goes wrong?

Production agents need an architecture that can answer that question. They need defined authority, durable state, safe recovery, and evidence that the intended action happened.

Microsoft’s September 16, 2026 article on building an agent harness in C# provides a timely starting point. It describes the runtime surrounding a model: the machinery for tools, planning, memory, approvals, and observation. These capabilities are available through Microsoft Agent Framework, although the application still owns its business boundaries. [1]

Here is how I would apply that thinking to an enterprise request system. The design below is a proposed architecture, not a report of a deployed implementation or a claim that one framework supplies every guarantee.

Define what the agent is allowed to finish

Consider an equipment request with attachments, eligibility rules, and a manager’s approval.

The agent can interpret an employee’s description, identify missing information, and prepare a submission. The application determines whether the employee may submit it, which approval path applies, and whether a state transition is valid.

That distinction gives each part of the system a clear responsibility:

Work Proposed owner
Understand a free-text description Model
Suggest a request category Model, validated against supported categories
Check eligibility and mandatory fields Application rules
Resolve the authorized approver Organization directory and policy
Explain what information is missing Model, using validation results
Approve a request Authorized approver or an explicit automatic approval policy
Persist the transition Application service and database

Microsoft’s workflow guidance supports combining model-driven steps with deterministic executors and human decision points. The developer decides where each belongs. [2]

For this example, “finished” needs a precise meaning. If the employee asked to submit a request, success means a request exists in the correct tenant and is awaiting the appropriate approval. It does not mean the equipment has been approved or ordered.

The interface should use those same distinctions. “Submitted and awaiting approval” is a much more useful result than “Done.”

Put a narrow contract around every action

I would expose operations such as GetRequest, ValidateDraft, and SubmitRequest. Each tool would call the existing application layer, with the same authorization and business validation used by other clients.

For submission, the proposed tool input would identify a saved draft and its expected version. The host would supply the authenticated identity and tenant scope. Neither would be accepted merely because the model included them in an argument. A background worker would retain the initiating user’s delegated scope and recheck authorization when executing an action; its service identity would not grant broader business authority.

The result would carry structured facts: request ID, persisted state, record version, and a failure category when applicable. That lets the agent explain a validation error without inventing whether a write succeeded.

Tool descriptions help the model choose an action. Enforcement belongs in the service that performs it.

If these tools are exposed through MCP, the protocol’s security requirements still apply. Its guidance explicitly rejects accepting tokens issued for another resource and passing them through unchecked to downstream services. Connecting a tool does not establish the caller’s authority to use every capability behind it. [3]

Build the context for the current decision

At submission time, our agent needs the current draft, relevant policy, validation results, and the employee’s unresolved questions. It rarely needs every conversation the employee has ever had.

Anthropic’s context engineering guidance describes context as a limited resource that must be curated throughout execution. It recommends retrieving relevant information as needed and managing accumulated history. Published in September 2025, it provides a foundational design principle. [4]

For this system, I would keep policy identifiers and effective dates beside retrieved rules. A conversation summary could help the agent remember why an employee changed a request, but the database would remain authoritative about its current status.

Attachments deserve a separate trust boundary. A document might contain text telling the agent to bypass approval. OWASP identifies instructions embedded in external material as a form of indirect prompt injection and recommends layered mitigations, including limited privileges and separation of untrusted content. [5]

In our design, an attachment supplies evidence for the request. It cannot create an approval, change the acting user’s role, or grant a tool additional permissions. Labels in the prompt help communicate this boundary; backend controls must enforce it.

Make approval a durable business event

A manager may respond tomorrow, after the worker has restarted and the employee has edited the draft.

Microsoft Agent Framework supports workflows that request external input and wait for a response. [6] For our application, I would build the approval record around the exact proposed change:

  • Request ID and version being approved.
  • Action and material details shown to the approver.
  • Verified approver identity and decision time.
  • Expiry and the recorded decision.

If the quantity or item changes, the old approval must not silently authorize the revised request. Execution should recheck the applicable policy and permissions, then atomically validate the relevant record version while committing the transition.

A timeout leaves the request pending, expired, or escalated according to business policy. It never becomes implicit consent.

This also keeps approvals useful. Reads and routine preparation can proceed under existing permissions, while the manager sees the consequential decision they are actually responsible for.

Design for the response that never arrives

Return to the opening example. The submission API committed a write, but the agent saw a timeout. The outcome is unknown from the caller’s perspective.

Microsoft’s Retry pattern documentation explicitly describes this failure mode and warns that repeating a non-idempotent operation can repeat its effects. [7]

For our request service, I would have the application generate and persist a stable operation ID before the first submission and reuse it for every retry of that same intended action. The service would enforce uniqueness within the correct tenant and operation scope, store the result, and reject reuse with a different payload.

The deduplication record and request transition need atomic handling. Otherwise, a crash between those writes recreates the ambiguity we were trying to remove. Concurrent retries also need to converge on one result. I would retain deduplication records for the supported retry and reconciliation window, and enforce a business rule preventing a submitted draft from becoming a second request under a new operation ID.

If submission succeeds but the manager’s notification fails, the request should remain submitted. A transactional outbox can record the business change and the event to be published in the same database transaction. A worker then delivers the event. Consumers must still handle duplicate delivery safely. [8]

External services complicate this further. If a downstream ordering system offers neither idempotency nor a reliable status lookup, our local database cannot guarantee that a timed-out order was not placed. Such a run needs reconciliation before another purchase attempt.

“Please be careful when retrying” would be a remarkably optimistic transaction strategy.

Keep business progress outside the conversation

The application should be able to answer “What happened to request 1842?” without asking the model to reconstruct it from chat history.

I would persist the run ID, current workflow step, request version, pending approval, attempted operations, confirmed results, and any unresolved external outcome. User-facing statuses should distinguish waiting for approval, submission confirmed, notification pending, and reconciliation required.

Microsoft’s Durable Extension provides infrastructure for persistence and recovery across worker executions. Its documentation also distinguishes durable execution from checkpoint storage in ordinary workflows. [9]

Neither capability removes the need to reason about external side effects. A checkpoint can record progress, but the interval between a remote write and recording its result still needs the idempotency or reconciliation design described above.

On recovery, the worker should inspect persisted progress and resolve outstanding operations before asking the model to plan again. The model should receive the resulting facts.

Give the run a budget and an explanation trail

A request assistant does not need unlimited attempts to find a department code.

I would set explicit limits on tool calls, elapsed time, retries, and model expenditure. Active execution time and the business deadline for a pending approval would have separate limits, so waiting overnight would not exhaust a model execution budget. Repeated attempts against the same missing dependency would trigger a controlled stop with a saved status and a useful next action. Permission failures would require a permission decision, rather than another attempt with slightly different wording.

For diagnosis, every run would have a correlation ID linking its model calls, tool invocations, policy decisions, approvals, and database transitions. Microsoft’s C# harness walkthrough includes OpenTelemetry instrumentation and token-usage observation as part of preparing an agent for production. [1]

Our telemetry should also record the model deployment, prompt version, tool schema version, and policy version. Those details help distinguish a model regression from a changed rule or failing integration.

I would keep credentials out of traces and avoid logging full attachments by default. Operational evidence needs its own access controls and retention rules.

The support team should be able to explain which action was attempted, under whose authority, and what the receiving system confirmed.

Test the outcome and the route taken

Anthropic’s January 2026 evaluation guidance distinguishes an agent’s transcript from the resulting state of its environment. It also recommends repeated trials because behavior can vary between runs. [10]

For this request assistant, I would start with the following evaluation cases:

Scenario Required result
Valid request One submission with the correct approval route
Missing attachment Specific clarification; no submission
Unauthorized record access Access denied without exposing the record
Attachment asks to bypass approval No unauthorized transition
Submission response is lost One request; existing result recovered or ambiguity surfaced
Draft changes after approval Old approval cannot authorize the changed request
Worker restarts while waiting Pending approval remains recoverable
Notification service fails Submission preserved; delivery tracked separately

Database assertions and tool-event checks should establish these properties. Language quality can be scored separately, using a defined rubric and human calibration where model graders are used. [10]

I would also include cancellation during execution. The system must distinguish stopping future work from reversing an operation that has already committed.

A passing run should satisfy the business outcome and its constraints. Repeat representative cases, preserve a holdout set, and rerun evaluations when changing models, prompts, tools, or retrieval behavior. A successful demonstration supplies a test case, not a reliability estimate.

Start with a small deployment boundary

For a .NET team, I would keep the first version close to the existing application architecture:

Component Responsibility
ASP.NET Core API Authentication, request intake, status, approval responses
Application services Authorization, validation, concurrency, business transitions
Agent runtime Interpretation, tool selection, clarification, explanations
Durable worker Persisted orchestration, bounded retries, recovery
Database and outbox Business state, operation results, pending events
Evaluation and telemetry Release evidence and production diagnosis

These are logical responsibilities. They can begin in one deployable application; separate services should follow actual scaling or isolation needs.

My proposed rollout would begin with preparation and recommendations using read-only integrations. A shadow evaluation could compare proposed actions against the real workflow, with writes disabled and appropriate handling of employee data. A limited pilot would then enable a small set of authorized writes.

Expansion should depend on demonstrated outcomes: correct routing, recovery from interruption, no observed unauthorized transitions in the release tests, and acceptable completion time and cost. Passing those tests reduces uncertainty; it does not prove failures are impossible.

The model earns its place by handling ambiguity that would otherwise burden employees. The surrounding application earns trust by making every consequential action controlled, recoverable, and verifiable.

Before connecting the next tool, decide what evidence will prove it completed its job—and what the system will do when that evidence is missing.
