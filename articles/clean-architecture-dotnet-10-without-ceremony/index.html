Clean Architecture in .NET 10: Stop Adding Layers, Start Protecting Decisions

A Clean Architecture codebase should not be judged by how many projects, interfaces, handlers, or patterns it contains. The useful question is simpler: which decisions are important enough to protect from change?

By Islam Darawsheh August 7, 2026 11 min read

Yesterday I argued that Clean Architecture and Domain-Driven Design are not competing alternatives. Today I want to make that argument concrete with one .NET 10 feature from HTTP request to domain model to persistence.

The feature is intentionally ordinary: place an order. The interesting part is not the endpoint. It is deciding where business authority lives, which dependencies deserve boundaries, and which abstractions we can deliberately avoid.

The rule for this example:

Add a boundary only when it protects policy, ownership, consistency, or a meaningful source of technical volatility.

Start with the decisions, not the projects

Before creating Domain, Application, Infrastructure, and Api projects, identify what can actually go wrong.

  • The client must not choose the product price.
  • An order quantity must be greater than zero.
  • An order cannot silently mix currencies.
  • Persistence must not define the domain model.
  • HTTP must not become the business layer.

Those are decisions worth protecting. The architecture exists to make those decisions difficult to violate.

UUIDv7 in .NET 10: still a Guid

One small modernization is worth making immediately. In .NET, the runtime type for a UUID is still Guid. We do not replace it with a new Uuid type. What changes is how we generate the value.

public readonly record struct OrderId(Guid Value)
{
    public static OrderId New() =>
        new(Guid.CreateVersion7());
}

Guid.CreateVersion7() creates an RFC 9562 UUID version 7. Unlike the random layout normally produced by Guid.NewGuid(), UUIDv7 contains time-ordered bits, which can be useful for application-generated identifiers and ordered ingestion.

Database caveat:

Do not turn “UUIDv7 is time ordered” into “every database index will automatically become sequential.” Database UUID comparison and storage semantics matter. Verify the actual provider—especially when using SQL Server uniqueidentifier—before making index-locality claims.

I also prefer a domain-specific ID wrapper over passing naked Guid values everywhere. It prevents accidentally supplying a CustomerId where a ProductId was expected, while keeping serialization and persistence boundaries free to use plain UUID values.

public readonly record struct ProductId(Guid Value);
public readonly record struct CustomerId(Guid Value);
public readonly record struct OrderId(Guid Value)
{
    public static OrderId New() =>
        new(Guid.CreateVersion7());
}

Put invariants in types that cannot ignore them

A quantity is not just an int if zero and negative values are invalid throughout the domain. Encoding that rule once is stronger than remembering to repeat an if statement in controllers, handlers, background jobs, and import processes.

public readonly record struct Quantity
{
    public int Value { get; }

    private Quantity(int value) => Value = value;

    public static Quantity From(int value)
    {
        if (value <= 0)
            throw new DomainException(
                "Quantity must be greater than zero.");

        return new Quantity(value);
    }
}

The same idea applies to money. A production model should not let unrelated currencies be added silently.

public readonly record struct Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    private Money(decimal amount, string currency)
    {
        Amount = amount;
        Currency = currency;
    }

    public static Money Of(decimal amount, string currency)
    {
        if (amount < 0)
            throw new DomainException("Money cannot be negative.");

        if (string.IsNullOrWhiteSpace(currency))
            throw new DomainException("Currency is required.");

        return new Money(
            decimal.Round(amount, 2, MidpointRounding.ToEven),
            currency.Trim().ToUpperInvariant());
    }

    public static Money Zero(string currency) => Of(0, currency);

    public Money Multiply(int quantity) =>
        Of(Amount * quantity, Currency);

    public static Money operator +(Money left, Money right)
    {
        if (!string.Equals(
                left.Currency,
                right.Currency,
                StringComparison.Ordinal))
        {
            throw new DomainException(
                "Cannot add different currencies.");
        }

        return Of(
            left.Amount + right.Amount,
            left.Currency);
    }
}

Whether two decimal places are universally correct is a separate domain question. The important point is that the rule has an owner. If the product later supports currencies with different minor-unit rules, this type is where that decision can evolve.

The aggregate should protect behavior, not mirror tables

public sealed class Order
{
    private readonly List<OrderItem> _items = [];

    private Order() { }

    private Order(
        OrderId id,
        CustomerId customerId,
        string currency)
    {
        Id = id;
        CustomerId = customerId;
        Currency = currency;
    }

    public OrderId Id { get; private set; }
    public CustomerId CustomerId { get; private set; }
    public string Currency { get; private set; } = string.Empty;
    public IReadOnlyCollection<OrderItem> Items => _items;

    public Money Total =>
        _items.Aggregate(
            Money.Zero(Currency),
            (sum, item) => sum + item.Subtotal);

    public static Order Create(
        CustomerId customerId,
        string currency)
    {
        if (string.IsNullOrWhiteSpace(currency))
            throw new DomainException("Currency is required.");

        return new Order(
            OrderId.New(),
            customerId,
            currency.Trim().ToUpperInvariant());
    }

    public void AddItem(
        ProductId productId,
        Money unitPrice,
        Quantity quantity)
    {
        if (!string.Equals(
                unitPrice.Currency,
                Currency,
                StringComparison.Ordinal))
        {
            throw new DomainException(
                "Order items must use the order currency.");
        }

        _items.Add(
            new OrderItem(
                productId,
                unitPrice,
                quantity));
    }
}
public sealed class OrderItem
{
    private OrderItem() { }

    internal OrderItem(
        ProductId productId,
        Money unitPrice,
        Quantity quantity)
    {
        ProductId = productId;
        UnitPrice = unitPrice;
        Quantity = quantity;
    }

    public ProductId ProductId { get; private set; }
    public Money UnitPrice { get; private set; }
    public Quantity Quantity { get; private set; }

    public Money Subtotal =>
        UnitPrice.Multiply(Quantity.Value);
}

This is not “DDD because it has entities.” The useful part is that invalid state transitions have fewer places to hide. The model owns behavior that must remain true regardless of whether the caller is HTTP, a message consumer, an admin tool, or a test.

The most important security decision: never trust the client price

An early version of this example could accept ProductId, Price, and Quantity in the command. That would make the code shorter—and the business rule wrong.

The request should contain what the customer is allowed to decide:

public sealed record PlaceOrderRequest(
    Guid CustomerId,
    IReadOnlyList<PlaceOrderItemRequest> Items);

public sealed record PlaceOrderItemRequest(
    Guid ProductId,
    int Quantity);

Notice what is missing: price. Pricing is authoritative server-side data. The application use case resolves it from a trusted catalog boundary.

Application ports should describe what the use case needs

public sealed record ProductSnapshot(
    ProductId Id,
    Money Price,
    bool IsActive);

public interface IProductCatalog
{
    Task<IReadOnlyDictionary<ProductId, ProductSnapshot>>
        GetByIdsAsync(
            IReadOnlyCollection<ProductId> productIds,
            CancellationToken cancellationToken);
}

public interface IOrderRepository
{
    Task AddAsync(
        Order order,
        CancellationToken cancellationToken);
}

public interface IUnitOfWork
{
    Task SaveChangesAsync(
        CancellationToken cancellationToken);
}

These interfaces are not there because every class needs an interface. They exist because product pricing, persistence, and transaction completion are external concerns whose implementations may change independently of the use case.

The use case: orchestration without stealing the domain's job

public sealed record PlaceOrderCommand(
    Guid CustomerId,
    IReadOnlyList<PlaceOrderLine> Items);

public sealed record PlaceOrderLine(
    Guid ProductId,
    int Quantity);

public sealed class PlaceOrderHandler(
    IProductCatalog catalog,
    IOrderRepository orders,
    IUnitOfWork unitOfWork)
{
    public async Task<OrderId> Handle(
        PlaceOrderCommand command,
        CancellationToken cancellationToken)
    {
        if (command.Items.Count == 0)
            throw new ValidationException(
                "At least one item is required.");

        var productIds = command.Items
            .Select(x => new ProductId(x.ProductId))
            .Distinct()
            .ToArray();

        var products = await catalog.GetByIdsAsync(
            productIds,
            cancellationToken);

        var missing = productIds
            .Where(id => !products.ContainsKey(id))
            .ToArray();

        if (missing.Length != 0)
            throw new ValidationException(
                "One or more products do not exist.");

        var currencies = products.Values
            .Select(x => x.Price.Currency)
            .Distinct(StringComparer.Ordinal)
            .ToArray();

        if (currencies.Length != 1)
            throw new ValidationException(
                "All products must use the same currency.");

        var order = Order.Create(
            new CustomerId(command.CustomerId),
            currencies[0]);

        foreach (var line in command.Items)
        {
            var productId = new ProductId(line.ProductId);
            var product = products[productId];

            if (!product.IsActive)
                throw new ValidationException(
                    $"Product {productId.Value} is not available.");

            order.AddItem(
                product.Id,
                product.Price,
                Quantity.From(line.Quantity));
        }

        await orders.AddAsync(
            order,
            cancellationToken);

        await unitOfWork.SaveChangesAsync(
            cancellationToken);

        return order.Id;
    }
}

There are two details here that matter more than the class name. First, the catalog lookup is batched instead of performing an N+1 query inside the loop. Second, the handler orchestrates; it does not reimplement quantity, money, or order invariants.

Infrastructure implements the boundary

EF Core belongs here because EF Core is a persistence choice. The application use case should not care whether the implementation uses PostgreSQL, SQL Server, or a different persistence adapter.

internal sealed class EfOrderRepository(
    OrderingDbContext dbContext)
    : IOrderRepository
{
    public Task AddAsync(
        Order order,
        CancellationToken cancellationToken)
    {
        return dbContext.Orders
            .AddAsync(order, cancellationToken)
            .AsTask();
    }
}

internal sealed class EfUnitOfWork(
    OrderingDbContext dbContext)
    : IUnitOfWork
{
    public async Task SaveChangesAsync(
        CancellationToken cancellationToken)
    {
        await dbContext.SaveChangesAsync(
            cancellationToken);
    }
}

Strong IDs can be mapped explicitly instead of forcing persistence primitives into the domain:

builder.Property(x => x.Id)
    .HasConversion(
        id => id.Value,
        value => new OrderId(value))
    .ValueGeneratedNever();

builder.Property(x => x.CustomerId)
    .HasConversion(
        id => id.Value,
        value => new CustomerId(value));

ValueGeneratedNever() communicates another real decision: the application creates the UUIDv7; the database does not replace it.

The HTTP endpoint should stay boring

app.MapPost(
    "/orders",
    async (
        PlaceOrderRequest request,
        PlaceOrderHandler handler,
        CancellationToken cancellationToken) =>
    {
        var command = new PlaceOrderCommand(
            request.CustomerId,
            request.Items
                .Select(x => new PlaceOrderLine(
                    x.ProductId,
                    x.Quantity))
                .ToArray());

        var orderId = await handler.Handle(
            command,
            cancellationToken);

        return Results.Created(
            $"/orders/{orderId.Value}",
            new { id = orderId.Value });
    });

There is no business rule in this endpoint. It translates transport data, calls the use case, and translates the result. That is exactly how interesting I want the presentation layer to be.

Tests should prove the decisions

Do not test layers because the diagram has layers. Test the behavior that justified the boundary.

[Fact]
public void Quantity_rejects_zero()
{
    var exception = Assert.Throws<DomainException>(
        () => Quantity.From(0));

    Assert.Equal(
        "Quantity must be greater than zero.",
        exception.Message);
}

A second test should prove that the total comes from trusted catalog pricing rather than client input. The API contract already helps: there is no price field for a malicious client to modify.

[Fact]
public async Task PlaceOrder_uses_authoritative_catalog_price()
{
    var productId = new ProductId(Guid.CreateVersion7());
    var customerId = Guid.CreateVersion7();

    var catalog = new FakeProductCatalog(
        new ProductSnapshot(
            productId,
            Money.Of(125m, "AED"),
            IsActive: true));

    var orders = new CapturingOrderRepository();
    var unitOfWork = new FakeUnitOfWork();

    var handler = new PlaceOrderHandler(
        catalog,
        orders,
        unitOfWork);

    await handler.Handle(
        new PlaceOrderCommand(
            customerId,
            [new PlaceOrderLine(productId.Value, 2)]),
        CancellationToken.None);

    Assert.NotNull(orders.AddedOrder);
    Assert.Equal(250m, orders.AddedOrder.Total.Amount);
    Assert.Equal("AED", orders.AddedOrder.Total.Currency);
}

The test is valuable because it protects a business and security decision. A test that merely verifies that a handler called a repository once is much less interesting unless that interaction itself represents required behavior.

What I deliberately did not add

Generic IRepository<T>

The use case needs orders, not an abstraction over every possible entity operation.

IOrderService + OrderManager

Extra pass-through layers do not create separation. They create navigation.

AutoMapper

Three explicit fields are clearer than adding a mapping dependency for ceremony.

MediatR by default

Useful when pipelines, behaviors, or dispatching justify it. Unnecessary when it only forwards one call.

Interface per class

Interfaces belong at meaningful boundaries, not beside every concrete type.

Database-shaped domain types

The persistence model adapts to business meaning, not the other way around.

So where is the Clean Architecture?

It is not in the number of folders. It is in the direction of authority.

HTTP Request
    │
    ▼
Application Use Case
    │
    ├──> Domain Model
    │      owns invariants
    │
    ├──> IProductCatalog
    │      trusted pricing boundary
    │
    └──> IOrderRepository / IUnitOfWork
           persistence boundary

Infrastructure ──implements──> Application ports

The domain does not know EF Core. The application does not know which database is underneath it. The endpoint does not decide price. Infrastructure does not own business rules.

That is enough architecture to protect the decisions we identified at the beginning.

When I would make it simpler

If this were a small internal CRUD screen with no meaningful invariants, no pricing authority, and no significant integration volatility, I would probably collapse several of these boundaries. Clean Architecture is not a tax every application must pay.

But once the business rules become expensive to violate, the boundaries start earning their keep.

Good architecture does not maximize abstraction. It makes important decisions explicit, testable, and difficult to accidentally bypass.

That is the version of Clean Architecture I want in a .NET 10 codebase: modern where modern features help, domain-focused where the business deserves protection, and intentionally boring everywhere else.
