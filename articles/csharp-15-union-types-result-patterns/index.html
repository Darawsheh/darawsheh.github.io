C# 15 Union Types: The End of Error-Prone Result Patterns?

How compiler-checked outcomes reshape API design, with practical validation, Minimal API mapping, JSON contracts, and the limits of native unions.

By Islam Darawsheh November 16, 2026 17 min read

An API that returns null when a record is missing, throws for a validation error, and returns a value on success may appear straightforward. But its signature communicates only one of those outcomes. The rest live in documentation, conventions, and the caller's memory.

Over time, teams try to fix this with bool flags, nullable tuples, Result<T> wrappers, marker interfaces, and exception hierarchies. Some of those designs are excellent. Others permit impossible states or make it too easy to forget a failure path.

C# 15, released with .NET 11 on November 10, 2026, adds another tool: union types. A union describes a closed set of possible types, and the compiler can check that a switch expression accounts for every case. This is a substantial improvement for outcome-driven APIs—but it is not the end of exceptions, and it is not automatically a replacement for every existing Result<T> library.

Let's examine exactly what the language guarantees, build a realistic ordering API, and test the tradeoffs at the serialization and performance boundaries.

The problem isn't exceptions. It's invisible outcomes.

Consider this signature:

Task<Order?> PlaceAsync(PlaceOrder command, CancellationToken ct);

What does null mean? Invalid input? An idempotent duplicate? A database outage? The type cannot tell us. We could use exceptions for the other cases, but callers would still need out-of-band knowledge of which exceptions represent expected business outcomes.

A tuple-based result looks more explicit:

public record OrderResult(
    bool Succeeded,
    Guid? OrderId,
    string? Error);

But its shape allows nonsensical states: Succeeded == true with a missing OrderId, or a successful response carrying an error. Defensive checks move into every consumer.

A properly designed custom Result<T> can already avoid many of these problems. The new contribution of unions is native composition of case types plus compiler-aware exhaustive matching, without requiring each case to inherit from a shared base class. Union types strengthen the choice of outcome; they do not automatically validate the fields inside each outcome.

Getting started: C# 15 is not a preview feature

Install the .NET 11 SDK and target net11.0. This is the minimal setup for a class library or console application; for the later Minimal API endpoint, use the ASP.NET Core Web SDK (Microsoft.NET.Sdk.Web), for example with dotnet new web -f net11.0:

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net11.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>
</Project>

C# 15 is the default language version for that target framework. Union types do not require <LangVersion>preview</LangVersion>. This matters because early .NET 11 previews did require extra setup, and older articles may still show it. The UnionAttribute and IUnion infrastructure are included in the released .NET 11 runtime; you do not need the hand-written polyfills used in early previews.

The core syntax is intentionally small (the following examples are teaching excerpts that assume normal SDK implicit usings):

public sealed record Accepted(Guid OrderId);
public sealed record Rejected(string Reason);

public union SubmissionOutcome(Accepted, Rejected);

SubmissionOutcome outcome = new Accepted(Guid.NewGuid());

string message = outcome switch
{
    Accepted accepted => $"Accepted {accepted.OrderId}",
    Rejected rejected => $"Rejected: {rejected.Reason}",
    null => "No outcome was supplied"
};

Accepted and Rejected are independent types. The union exposes implicit conversions from each case type. In a type pattern such as Accepted accepted, the compiler tests the contained value, not the union wrapper.

Notice that the example uses null, not _, for its final arm. That distinction will matter when we evolve the contract.

A real application boundary: placing an order

Let's model three expected outcomes:

  • An order was created.
  • The command failed validation.
  • The idempotency key has already been used.

The application layer can communicate those outcomes without depending on HTTP status codes. Validation is not necessarily a single error: a request can contain multiple independent problems, and clients should be able to correct all of them in one iteration. The validation case therefore holds a structured collection of errors, each with a stable code, an input field, and a human-readable message.

public sealed record PlaceOrder(
    Guid ProductId,
    int Quantity,
    string IdempotencyKey);

public sealed record OrderPlaced(Guid OrderId);

public sealed record ValidationError(
    string Code,
    string Property,
    string Message);

// Keep the error collection nonempty and prevent callers from mutating it.
public sealed record InvalidOrder
{
    public IReadOnlyList<ValidationError> Errors { get; }

    public InvalidOrder(IEnumerable<ValidationError> errors)
    {
        ArgumentNullException.ThrowIfNull(errors);
        var snapshot = errors.ToArray();

        if (snapshot.Length == 0)
            throw new ArgumentException(
                "At least one validation error is required.", nameof(errors));

        Errors = Array.AsReadOnly(snapshot);
    }
}

public sealed record DuplicateRequest(string IdempotencyKey);

public union PlaceOrderOutcome(
    OrderPlaced,
    InvalidOrder,
    DuplicateRequest);

public interface IOrders
{
    // Simplified contract: null means the key was previously used.
    // Enforce uniqueness atomically (for example, in the database).
    Task<Guid?> TryCreateAsync(PlaceOrder command, CancellationToken ct);
}

public sealed class PlaceOrderHandler(IOrders orders)
{
    public async Task<PlaceOrderOutcome> HandleAsync(
        PlaceOrder command,
        CancellationToken ct)
    {
        var errors = new List<ValidationError>();

        if (command.ProductId == Guid.Empty)
            errors.Add(new(
                "PRODUCT_REQUIRED", nameof(command.ProductId),
                "Product is required."));

        if (command.Quantity <= 0)
            errors.Add(new(
                "INVALID_QUANTITY", nameof(command.Quantity),
                "Quantity must be greater than zero."));

        if (string.IsNullOrWhiteSpace(command.IdempotencyKey))
            errors.Add(new(
                "IDEMPOTENCY_KEY_REQUIRED", nameof(command.IdempotencyKey),
                "Idempotency key is required."));

        if (errors.Count > 0)
            return new InvalidOrder(errors);

        Guid? orderId = await orders.TryCreateAsync(command, ct);

        if (orderId is null)
            return new DuplicateRequest(command.IdempotencyKey);

        return new OrderPlaced(orderId.Value);
    }
}

Because validation collects independent errors before returning, the caller gets actionable feedback in one response. The order of these checks is intentional: do not call the repository when the command is invalid. More complex systems should keep field-level validation distinct from business invariants that require state or concurrency checks. Stable error codes are for programmatic handling; messages can be localized without changing client logic.

The InvalidOrder constructor makes a defensive copy and rejects an empty collection. This matters because a union prevents an invalid combination of cases, not an invalid payload within a case. Without that guard, new InvalidOrder([]) would be legal even though a failure with zero errors is contradictory. For an application using a validation library, the same invariant can be enforced in a reusable nonempty error collection.

This is deliberately not an exception-free architecture. Infrastructure failures, programming defects, and cancellation still need appropriate handling. The union represents expected, modeled outcomes. Do not turn every unforeseen exception into a bland UnknownFailure case and lose the context needed for diagnosis.

There is also a concurrency detail worth preserving: checking for an existing idempotency key and then inserting a row in two unrelated database calls is racy. The repository contract above assumes atomic enforcement, typically backed by a database uniqueness constraint.

Idempotency caveat: This teaching example treats every reused key as a conflict so that the union stays small. Its DuplicateRequest outcome is therefore a simplified uniqueness rejection, not a complete implementation of idempotent request replay. A production idempotent endpoint ordinarily stores a fingerprint of the original request and its response: a retry with the same key and equivalent payload can replay the earlier response, while the same key with a different payload is a conflict. Do not copy the TryCreateAsync contract unchanged into a payment or other high-stakes API. The main point here is how to model expected results, not a complete idempotency protocol.

Mapping the union to a Minimal API

At the HTTP boundary, each outcome gets an explicit status code. We use a separate response DTO for validation, keeping transport contracts out of the application layer:

public sealed record ValidationErrorResponse(
    IReadOnlyList<ValidationError> Errors);

app.MapPost("/orders", async (
    PlaceOrder command,
    PlaceOrderHandler handler,
    CancellationToken ct) =>
{
    PlaceOrderOutcome outcome =
        await handler.HandleAsync(command, ct);

    IResult response = outcome switch
    {
        OrderPlaced placed =>
            TypedResults.Created($"/orders/{placed.OrderId}", placed),

        InvalidOrder invalid =>
            TypedResults.BadRequest(new ValidationErrorResponse(invalid.Errors)),

        DuplicateRequest duplicate =>
            TypedResults.Conflict(duplicate),

        null => TypedResults.Problem(
            "An unexpected error occurred.")
    };

    return response;
})
.Produces<OrderPlaced>(StatusCodes.Status201Created)
.Produces<ValidationErrorResponse>(StatusCodes.Status400BadRequest)
.Produces<DuplicateRequest>(StatusCodes.Status409Conflict)
.ProducesProblem(StatusCodes.Status500InternalServerError);

For example, an invalid command with three independent input errors returns a single 400 Bad Request containing all three errors:

{
  "errors": [
    { "code": "PRODUCT_REQUIRED", "property": "ProductId", "message": "Product is required." },
    { "code": "INVALID_QUANTITY", "property": "Quantity", "message": "Quantity must be greater than zero." },
    { "code": "IDEMPOTENCY_KEY_REQUIRED", "property": "IdempotencyKey", "message": "Idempotency key is required." }
  ]
}

TypedResults.ValidationProblem is another option if your API standardizes on ValidationProblemDetails, whose errors are grouped by property name; however, that default shape does not preserve our separate machine-readable codes. Here, a purpose-built response keeps the full ValidationError contract. Pick one error format across your service and document it.

This maps business outcomes to 201, 400, and 409 without leaking IResult into the application layer. It also explicitly handles the uninitialized/default union case. The .Produces<T>() calls document the response contracts that an IResult return type would not otherwise preserve; .ProducesProblem() advertises the defensive 500 path. These calls supply metadata, not runtime validation of the endpoint's actual behavior, and an OpenAPI generator must be configured to emit the document. In a real API, register PlaceOrderHandler and IOrders with dependency injection, avoid exposing sensitive error details, and test that runtime responses match the declared metadata.

ASP.NET Core also offers Results<T1, T2, ...> for strongly typed HTTP result alternatives. That solves a transport-layer concern (including metadata inference), not the same problem as a C# union of application-layer outcomes.

A final distinction: malformed JSON or a body that cannot be deserialized can fail during ASP.NET Core binding, before this handler runs. Aggregated business-validation errors are not a promise that all protocol/binding failures will use the same shape. Standardize those errors separately if the client contract requires it.

Exhaustiveness: the most important benefit

Suppose the business introduces a fourth outcome:

public sealed record RateLimited(TimeSpan RetryAfter);

public union PlaceOrderOutcome(
    OrderPlaced,
    InvalidOrder,
    DuplicateRequest,
    RateLimited);

Our existing switch expression no longer covers every case. C# issues an exhaustiveness warning (typically CS8509) and identifies the missing pattern. With a build policy that treats the relevant warnings as errors, this becomes a CI gate. Without that policy, it is a warning, not a universal compile-time error.

This is why the distinction between these two fallbacks matters:

// Discouraged when the point is future-case exhaustiveness:
_ => TypedResults.Problem("Unexpected outcome")

// Preferred for handling the generated struct's empty state:
null => TypedResults.Problem("Uninitialized outcome")

A discard (_) matches new case types too, hiding the warning when the union grows. A null arm covers only the empty case and leaves new outcomes visible to the compiler.

The exhaustiveness feature applies to switch expressions. Do not assume an ordinary if chain or switch statement gives you the same completeness guarantee. A useful CI policy is to elevate CS8509 and the nullable-pattern warning CS8655 to errors; treat the latter as an additional safeguard, not as a substitute for deliberately handling default.

The subtle default and null trap

A generated union is a struct, with a stored object? value. Its default value is therefore valid as a .NET struct value but contains no active case:

PlaceOrderOutcome outcome = default;
Console.WriteLine(outcome.Value is null); // True

This can happen in default-initialized fields, array elements, or framework-created objects. Even if every declared case type is non-nullable, C# does not necessarily warn when your switch omits the null arm. A case-only switch can then throw SwitchExpressionException at runtime.

The practical rule is: handle null explicitly wherever an uninitialized union could arrive, especially at public boundaries. That arm is not a replacement for normal input validation. It is a safeguard against a real limitation of the representation.

Another subtlety: union does not produce an F#-style tagged discriminated union automatically. The cases are types, not separately named tags. If you need two outcomes that both carry string, create distinct case records instead of trying to rely on the payload type alone.

public sealed record EmailAccepted(string Address);
public sealed record EmailRejected(string Reason);
public union EmailOutcome(EmailAccepted, EmailRejected);

For generic results, wrappers are particularly valuable:

public sealed record Ok<T>(T Value);
public sealed record NotFound(string Resource, string Key);
public sealed record ValidationFailed(IReadOnlyList<string> Errors);

public union QueryOutcome<T>(
    Ok<T>,
    NotFound,
    ValidationFailed);

Using Ok<T> avoids overlap when T happens to be an error type. It also provides a place to attach future success-specific behavior. Unions do allow overlapping case types, but ambiguous implicit conversions and overlapping patterns can make contracts harder to reason about.

What actually gets generated—and why performance is not free

Conceptually, a union declaration is lowered to a struct with a constructor for each case and a single object?-backed Value property:

// Conceptual approximation, not compiler-generated source:
public struct SubmissionOutcomeConcept
{
    public SubmissionOutcomeConcept(Accepted value) => Value = value;
    public SubmissionOutcomeConcept(Rejected value) => Value = value;

    public object? Value { get; }
}

The real generated type is marked with UnionAttribute and implements IUnion; the compiler adds its union-specific conversion and matching behavior. The approximation above only illustrates the storage model.

This has important consequences:

  • A value-type case such as int, Guid, or decimal is boxed by the generated union.
  • Reference-type cases are held through the object? reference; the union wrapper itself is a struct.
  • A case modeled as a record class has its own allocation characteristics. A union does not erase them.
  • A union is not inherently faster than a hand-tuned Result<T> using dedicated fields and a tag.

For hot paths, C# 15 also recognizes custom unions marked with [Union]. Those types can provide HasValue and typed TryGetValue members so the compiler can perform matching without boxing value types. The official tutorial includes a custom numeric union that demonstrates this pattern.

The recommendation is simple: choose unions for modeling clarity first, and benchmark before claiming a throughput or allocation win. Measure your actual case distribution, allocation rate, and serializer behavior with BenchmarkDotNet rather than assuming the keyword is a performance optimization.

JSON, ASP.NET Core, and OpenAPI: more capable than you might expect

A common concern with new language constructs is whether they work at API boundaries. In .NET 11, System.Text.Json has native union serialization and deserialization support. It serializes the active case value, rather than a { "Value": ... } envelope:

using System.Text.Json;

public sealed record Message(string Text);
public union Payload(int, string, Message);

Payload payload = new Message("Ready");
string json = JsonSerializer.Serialize(payload);

// {"Text":"Ready"}

Writing is straightforward. Reading can be ambiguous. The default classifier distinguishes JSON token kinds: a number, string, Boolean, object, or array. Two record cases generally both look like JSON objects, so the serializer cannot identify one merely from the token kind.

.NET 11 offers a structural classifier for distinguishable object shapes:

using System.Text.Json;
using System.Text.Json.Serialization;

[JsonUnion(TypeClassifier = typeof(JsonUnionTypeStructuralClassifier))]
public union Pet(Dog, Cat);

public sealed record Dog(string Name, string Breed);
public sealed record Cat(string Name, int Lives);

A JSON object containing Breed can be classified as Dog; one containing Lives can be classified as Cat. But overlapping properties, changes to contract shapes, and certain nested or polymorphic cases can defeat structural classification. There are custom classifiers for advanced needs.

There is a more surprising edge case: under ASP.NET Core's web JSON defaults, numbers can sometimes be read from JSON strings. A union of int and string can therefore be ambiguous on input, even though its two output shapes are obvious. Test both the serialize and deserialize paths using the actual production options.

ASP.NET Core 11 supports unions in JSON request/response bodies, including Minimal APIs and MVC; its JSON-based SignalR and relevant Blazor serialization paths also support them. It does not directly bind union values from route parameters, query strings, headers, or form fields. OpenAPI generation represents a union's possible schemas using anyOf. That support does not absolve you from documenting the distinct HTTP status codes returned by your own IResult mapping.

For a new public JSON contract whose cases are all classes you own, consider the other C# 15 feature: closed hierarchies. Paired with [JsonPolymorphic(InferClosedTypePolymorphism = true)], they can emit an explicit $type discriminator and give clients more stable case identification when object shapes overlap. Unions are especially compelling when composing unrelated existing types or preserving an existing discriminator-free format.

ExceptionsUsually notNoAppropriate for exceptional failures; poor as an implicit catalog of routine outcomes
T? / nullable returnOnly success vs. absenceNoToo little information when failure has several meanings
Boolean flag / tuplePartiallyNoCan permit contradictory or incomplete states
Hand-written Result<T>Yes, if carefully designedDepends on its API and analyzersCan offer ergonomic helpers and efficient storage, but often requires more infrastructure

A mature Result library may still be preferable when your team relies on Map, Bind, Match, Tap, async composition, validation accumulation, or a stable cross-target-framework API. Native unions do not automatically provide that entire functional vocabulary. And a custom library can opt into C# 15 union matching by implementing the documented [Union] shape—it need not be replaced wholesale.

Adoption guidelines for production teams

  1. Start at one application boundary. Try a query handler or command handler with three or four well-defined outcomes, not a repository-wide conversion.
  2. Name cases semantically. OrderPlaced and DuplicateRequest convey intent better than string and Exception.
  3. Return multiple independent validation errors together. Use stable machine-readable codes and property paths rather than a single unstructured string; do not confuse predictable input errors with infrastructure failures.
  4. Keep unexpected failures exceptional. Preserve telemetry, stack traces, cancellation, and retry semantics rather than forcing all failures into a union.
  5. Use exhaustive switch expressions and explicit null handling. Avoid _ in switches meant to flag newly added cases; consider treating exhaustiveness warnings as CI errors.
  6. Keep transport concerns at the boundary. HTTP results, JSON shapes, and error contracts should not drive domain-type design accidentally; document status codes and response schemas explicitly.
  7. Test real integration behavior. Cover serialization round-trips, ambiguous JSON cases, OpenAPI output, default-initialized unions, and allocation-sensitive scenarios. Verify that invalid requests return all independent errors and that a reused key follows your chosen idempotency policy.
  8. Respect framework constraints. Teams staying on .NET 10 LTS can retain their existing Result patterns; .NET 11 is an STS release, so a migration should be justified by benefits beyond adopting a keyword.

Production implementation checklist

These examples are intended for an SDK-style net11.0 project. Before treating these examples as production-tested guidance, compile the code with the released .NET 11 SDK and exercise the complete endpoint with a real IOrders implementation. At minimum, verify:

  • The three ordinary outcomes and the default(PlaceOrderOutcome) path.
  • A request with several invalid fields returns all error codes and properties in a single 400 response.
  • OpenAPI documents 201, 400, 409, and 500 with the intended response schemas.
  • Repeated keys are handled atomically, and the documented production replay/conflict semantics are implemented if adopting this design beyond the teaching sample.
  • JSON serialize/deserialize behavior under the actual ASP.NET Core serializer settings, including ambiguous union cases.
  • An intentionally omitted union case triggers a compiler warning; configure the build to fail on that warning.

The article's snippets are focused teaching excerpts, not a complete deployable API: dependency-injection registrations, persistence, authentication, exception handling, and integration tests are intentionally outside their scope.

So, is this the end of Result<T>?

No—and that's precisely what makes C# 15 unions interesting.

The real advance is not that developers can finally return “success or failure.” They have been doing that for years. The advance is that the language now understands a closed set of outcomes, offers concise implicit conversions, and can warn when a caller forgets an added case.

For many application services, this removes boilerplate and makes the contract harder to misuse. For other workloads, a carefully implemented Result type, a closed hierarchy, or an exception remains the better abstraction. A union is an additional design tool, not an architectural ideology.

The question to ask in code review is therefore not “Can we replace our Result library?” It is: “Can a reader see every expected outcome in the type signature—and will the compiler tell us when that contract changes?”

If the answer becomes yes, union types have already earned their place.
