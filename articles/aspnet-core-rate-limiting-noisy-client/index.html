One Noisy Client Can Slow Everyone Down—Fix Your ASP.NET Core Rate Limiting

Rate limiting is not just “100 requests per minute.” The partition key decides who competes for those 100 requests, while endpoint cost, queueing, proxy topology, and deployment scale decide whether the policy actually protects the resource you care about.

By Islam Darawsheh August 14, 2026 14 min read

Rate limiting looks deceptively simple. Pick a number, choose a window, add the middleware, and assume the API is protected. But a limit without a clearly defined owner can enforce the exact number you configured and still protect the wrong thing.

PermitLimit = 100;
Window = TimeSpan.FromMinutes(1);

The more important question is:

Who owns those 100 requests?

Every authenticated user? Every API client? Every IP address? One endpoint? One application instance? Or everybody who happens to share the same bucket?

The principle for this article:

Do not choose a rate limit until you know who is supposed to share it and which resource the limit is supposed to protect.

Keep three clients in mind

Assume an ASP.NET Core 10 API serves three customers:

Customer A → 20 requests/min
Customer B → 15 requests/min
Customer C → 25 requests/min

Then Customer A deploys a buggy polling loop:

Customer A → 500 requests/min

What should happen?

Customer A
    ↓
hits its own limit
    ↓
429 Too Many Requests

Customer B → unaffected
Customer C → unaffected

That behavior is only possible if the limiter models those customers as separate partitions.

Microsoft describes rate-limit partitions as independent buckets with separate counters, commonly keyed by user ID, IP address, API key, or another application-specific value. The benefit is fairness: one caller does not have to consume everybody else's allowance.

The dangerous version: everyone shares one bucket

This limiter is valid code:

options.GlobalLimiter =
    PartitionedRateLimiter.Create<HttpContext, string>(
        _ => RateLimitPartition.GetFixedWindowLimiter(
            partitionKey: "all-clients",
            factory: _ => new FixedWindowRateLimiterOptions
            {
                PermitLimit = 100,
                Window = TimeSpan.FromMinutes(1),
                QueueLimit = 0,
                AutoReplenishment = true
            }));

But it creates this model:

                    100 requests/min
                           │
               ┌───────────┼───────────┐
               │           │           │
               A           B           C

Customer A can consume the shared allowance and cause unrelated customers to be rejected. If queueing is enabled, unrelated callers can also be forced to wait behind traffic they did not generate.

The limiter is working exactly as configured. The problem is that the configuration modeled the wrong ownership boundary.

GlobalLimiter does not mean one global bucket

This terminology is easy to misread:

options.GlobalLimiter

GlobalLimiter means the limiter is applied broadly to requests. It does not require one shared counter for the entire application.

Microsoft's ASP.NET Core documentation configures GlobalLimiter with PartitionedRateLimiter, including examples that partition by authenticated identity or IP address.

So the design question is not:

Global limiter or partitioned limiter?

A global limiter can itself be partitioned. The better question is:

Which partition should this request belong to?

Authenticated clients should normally compete with themselves

Suppose the business rule is:

Standard client → 100 requests/min
Premium client  → 1,000 requests/min

A stable authenticated client identity is a natural partition key:

Client A → Bucket A
Client B → Bucket B
Client C → Bucket C

The important word is authenticated. I do not want an arbitrary caller-controlled string to manufacture unlimited partitions simply by changing a request header.

A stronger model is:

credential
   ↓
authentication
   ↓
validated client identity
   ↓
partition key

For example, the application might use a validated client_id or sub claim produced by its authentication layer rather than the raw credential itself.

Middleware order matters when the limiter uses identity

If the partitioner reads HttpContext.User, authentication must run before the limiter needs that identity.

Microsoft's authenticated-user rate-limiting sample uses this order:

app.UseRouting();
app.UseAuthentication();
app.UseRateLimiter();
app.UseAuthorization();

If authentication has not populated HttpContext.User, code such as this can collapse callers into the same fallback partition:

context.User.FindFirst("client_id")?.Value
    ?? "anonymous"

That can quietly turn a per-client design back into a shared bucket.

A complete production-shaped example

The following example combines four decisions:

  • Authenticated clients get separate global buckets.
  • Premium clients get a larger allowance.
  • Anonymous traffic falls back to an IP partition.
  • An expensive export endpoint also gets a concurrency limit.
using System.Globalization;
using System.Threading.RateLimiting;
using Microsoft.AspNetCore.RateLimiting;

var builder = WebApplication.CreateBuilder(args);

builder.Services
    .AddAuthentication("Bearer")
    .AddJwtBearer();

builder.Services.AddAuthorization();

builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode =
        StatusCodes.Status429TooManyRequests;

    options.OnRejected = async (context, cancellationToken) =>
    {
        if (context.Lease.TryGetMetadata(
            MetadataName.RetryAfter,
            out var retryAfter))
        {
            context.HttpContext.Response.Headers.RetryAfter =
                ((int)retryAfter.TotalSeconds)
                    .ToString(CultureInfo.InvariantCulture);
        }

        await context.HttpContext.Response.WriteAsJsonAsync(
            new
            {
                error = "rate_limit_exceeded"
            },
            cancellationToken);
    };

    options.GlobalLimiter =
        PartitionedRateLimiter.Create<HttpContext, string>(
            httpContext =>
            {
                var clientId =
                    httpContext.User.FindFirst("client_id")?.Value
                    ?? httpContext.User.FindFirst("sub")?.Value;

                if (clientId is null)
                {
                    var ip =
                        httpContext.Connection.RemoteIpAddress?.ToString()
                        ?? "unknown";

                    return RateLimitPartition.GetFixedWindowLimiter(
                        partitionKey: $"anonymous:{ip}",
                        factory: _ => new FixedWindowRateLimiterOptions
                        {
                            PermitLimit = 30,
                            Window = TimeSpan.FromMinutes(1),
                            QueueLimit = 0,
                            AutoReplenishment = true
                        });
                }

                var isPremium = string.Equals(
                    httpContext.User.FindFirst("tier")?.Value,
                    "premium",
                    StringComparison.OrdinalIgnoreCase);

                var tier = isPremium ? "premium" : "standard";
                var permitLimit = isPremium ? 1_000 : 100;

                return RateLimitPartition.GetFixedWindowLimiter(
                    partitionKey: $"client:{clientId}:{tier}",
                    factory: _ => new FixedWindowRateLimiterOptions
                    {
                        PermitLimit = permitLimit,
                        Window = TimeSpan.FromMinutes(1),
                        QueueLimit = 0,
                        AutoReplenishment = true
                    });
            });

    options.AddConcurrencyLimiter(
        policyName: "report-export",
        configureOptions: limiter =>
        {
            limiter.PermitLimit = 3;
            limiter.QueueProcessingOrder =
                QueueProcessingOrder.OldestFirst;
            limiter.QueueLimit = 0;
        });
});

var app = builder.Build();

// If a reverse proxy is used, configure trusted forwarded
// headers before relying on RemoteIpAddress.
app.UseForwardedHeaders();

app.UseRouting();
app.UseAuthentication();
app.UseRateLimiter();
app.UseAuthorization();

app.MapPost(
        "/reports/export",
        () => Results.Accepted())
    .RequireAuthorization()
    .RequireRateLimiting("report-export");

app.Run();

This is intentionally not a universal copy-and-paste policy. The numbers are placeholders. The useful part is the shape:

stable client identity
        ↓
per-client request-rate bucket
        ↓
endpoint-specific resource protection
        ↓
explicit rejection contract

There is a subtle reason the example includes the tier in the partition key. PartitionedRateLimiter.Create reuses a cached limiter when the partition key matches an existing entry. If a client's limit can change from standard to premium while the application is running, a key containing only clientId can keep reusing the previously created limiter. In a real system, make policy changes deliberate—for example by including a trusted tier or policy version in the key, or by using another strategy that replaces the intended limiter state. A policy-key change also starts a new bucket, so that reset should be an explicit product decision.

Also notice that the concurrency policy is shared for the export endpoint. That is deliberate: the resource we are protecting there is not one customer's fairness allowance; it is the application's ability to run only a small number of expensive exports at once.

IP-based limiting becomes an infrastructure problem

Anonymous endpoints may not have an authenticated identity:

/login
/register
/password-reset
/public-search

An IP address can be one useful signal, and Microsoft demonstrates IP-based rate-limit partitions. But once a reverse proxy or load balancer sits in front of the application, the address ASP.NET Core sees may initially be the proxy address rather than the original client's address.

Client A ─┐
Client B ─┼→ Reverse Proxy → ASP.NET Core
Client C ─┘

If every request appears to originate from the proxy, this partition key:

context.Connection.RemoteIpAddress

can accidentally place many real clients into one bucket.

ASP.NET Core's forwarded-header guidance explains that proxy servers obscure the originating address and that trusted forwarded headers are required when the application needs that original client information.

Do not blindly trust X-Forwarded-For

The opposite mistake is accepting forwarded headers from anybody.

Current ASP.NET Core behavior is deliberately hardened: forwarded headers from unknown proxies are ignored unless those proxies or networks are configured as trusted. Microsoft recommends reviewing the deployment topology and configuring KnownProxies or KnownNetworks appropriately.

Internet Client
      ↓
Trusted Proxy
      ↓
X-Forwarded-For
      ↓
Forwarded Headers Middleware
      ↓
RemoteIpAddress
      ↓
Rate Limiter

An IP-based limiter is only as trustworthy as the infrastructure that established the IP.

There is another warning about partition keys

Microsoft's rate-limiting guidance warns that creating partitions directly from user input can itself create a denial-of-service risk.

The reason is architectural: a partitioned limiter keeps limiter state for distinct partition keys. If an attacker can cheaply generate effectively unbounded unique keys, the application may be forced to create and retain unnecessary limiter state.

That is another reason to prefer bounded, validated identities such as authenticated user IDs or registered client IDs over arbitrary request strings.

Who owns the quota is only half the design

After deciding who owns the limit, decide what resource needs protection.

ASP.NET Core provides four main algorithms:

Fixed Window
Sliding Window
Token Bucket
Concurrency

Microsoft distinguishes them in an important way: fixed-window, sliding-window, and token-bucket limiters constrain request volume over time, while the concurrency limiter constrains how many requests are executing at once.

Microsoft also recommends considering endpoint cost—such as time, data access, CPU, and I/O—when selecting a limiter.

A cheap lookup and an expensive export are not the same resource

Compare:

GET /products/123

with:

POST /reports/export

The first may be a quick indexed lookup. The second might run several queries, allocate large buffers, generate a document, and hold CPU or I/O resources for seconds.

A single rule such as:

100 requests/minute

does not express those two resource profiles very well.

For an expensive operation, a concurrency rule can be more meaningful:

Maximum 3 report exports executing at once

That can sit on top of a per-client global request-rate policy.

Global and endpoint-specific limits can work together

A useful architecture can look like this:

Request
   ↓
per-client global limit
   ↓
endpoint-specific limit
   ↓
application work

Microsoft's samples explicitly note that when both exist, the global limiter runs before the endpoint-specific limiter.

ASP.NET Core and System.Threading.RateLimiting also support chained limiters when multiple constraints should be evaluated as one combined limiter. That is useful when the rules really represent one composed resource policy rather than unrelated middleware decoration.

Queueing is a product decision too

Most limiter options can queue requests when permits are unavailable:

QueueLimit = 10;
QueueProcessingOrder = QueueProcessingOrder.OldestFirst;

But queueing changes the failure mode.

QueueLimit = 0
    ↓
reject quickly

QueueLimit > 0
    ↓
wait for a permit
    ↓
request latency increases
    ↓
caller may still timeout

For a latency-sensitive HTTP API, I would not enable a queue simply because the framework supports one. Sometimes a clear 429 is a healthier contract than hiding overload behind growing latency.

For long-running work, the more important architecture question may be whether the operation belongs in an application-level background job queue rather than in an HTTP rate-limiter queue.

429 is not the middleware default

This is one ASP.NET Core detail worth making explicit.

RateLimiterOptions.RejectionStatusCode defaults to:

503 Service Unavailable

not:

429 Too Many Requests

For ordinary client throttling, I usually prefer to make the contract explicit:

options.RejectionStatusCode =
    StatusCodes.Status429TooManyRequests;

OnRejected can then add application-specific response content and a Retry-After header when the limiter provides that estimate.

Retry-After depends on the algorithm

Microsoft's official samples call out an important difference:

  • Fixed window can estimate retry time.
  • Sliding window can estimate retry time.
  • Token bucket can estimate retry time.
  • Concurrency limiting cannot predict when an in-flight request will finish.

So a generic policy that promises a meaningful Retry-After value for every limiter type would be misleading.

Application rate limiting is not complete DDoS protection

Rate limiting can mitigate abuse and some denial-of-service pressure, but Microsoft explicitly says it is not a comprehensive DDoS solution.

Think in layers:

Internet
   ↓
CDN / WAF / DDoS protection
   ↓
reverse proxy / gateway
   ↓
ASP.NET Core rate limiting
   ↓
authorization
   ↓
business operation

Application rate limiting is valuable because it understands application identity, endpoint cost, and product policy. It should not pretend to replace infrastructure designed to absorb large distributed attacks.

The multi-instance trap

Suppose the API is deployed on four replicas:

Load Balancer
    │
    ├── Instance 1
    ├── Instance 2
    ├── Instance 3
    └── Instance 4

and the application configures:

100 requests/min per client

The built-in System.Threading.RateLimiting implementations are in-memory. An official ASP.NET Core issue requesting a Redis-backed limiter specifically describes the need for a limiter that works across multiple hosts in a distributed environment.

So do not silently interpret an in-process limiter as:

100 requests/min across the entire cluster

unless the architecture actually coordinates that quota at a shared layer.

Depending on the requirement, cluster-wide enforcement may belong at a gateway, reverse proxy, edge service, or a distributed limiter backed by shared state.

Ask this before scaling out:

Is the quota supposed to be per process, per instance, or per client across the entire service? Those are different guarantees.

Measure the limiter, do not just configure it

ASP.NET Core exposes built-in rate-limiting metrics, and Microsoft's guidance explicitly recommends stress testing rate-limit configurations before production deployment.

A useful test plan should include more than the happy path:

  • One client exhausting only its own partition.
  • Several clients staying independent under load.
  • Anonymous traffic behind the real proxy topology.
  • Premium and standard tiers receiving different limits.
  • Expensive endpoints reaching concurrency limits.
  • Queue-disabled requests failing quickly.
  • Correct 429 and Retry-After behavior.
  • Multiple application instances if cluster-wide quotas matter.

The design I would ship

For an authenticated API, my starting model would be:

Request
   ↓
trusted forwarded-header processing
   ↓
authentication
   ↓
resolve stable client/user identity
   ↓
partitioned global rate limit
   │
   ├── Client A bucket
   ├── Client B bucket
   └── Client C bucket
   ↓
optional endpoint-specific protection
   ↓
application work

And I would answer these questions explicitly:

  • Who owns the quota?
  • Which callers are allowed to share a bucket?
  • What resource is being protected?
  • Is the constraint request rate or concurrency?
  • Can callers wait, or should they fail fast?
  • What does a rejection look like?
  • Is Retry-After meaningful for this algorithm?
  • Does the application run behind trusted proxies?
  • Is the quota per instance or cluster-wide?

Only after those questions are answered would I choose the number:

100 requests/minute

What I would not standardize

  • One shared bucket for every authenticated user.
  • IP limiting without understanding the proxy chain.
  • Arbitrary untrusted strings as unbounded partition identities.
  • The same limiter for cheap and expensive endpoints.
  • Queueing simply because QueueLimit exists.
  • Implicit 503 when the API contract intends 429.
  • Application rate limiting as the only DDoS defense.
  • Per-process counters presented as cluster-wide quotas.
  • Production limits chosen without load testing.
A rate limiter can enforce the exact number you configured and still protect the wrong thing.

The quality of the design comes from the boundary around the number: whose traffic shares it, which resource it protects, where its state lives, and what the caller experiences when the limit is reached.
