TokenOps: The Missing Discipline for AI Agents in Production

Production AI agents need more than billing dashboards: observe each run, attribute its cost, enforce budgets, and measure accepted outcomes.

By Islam Darawsheh October 8, 2026 18 min read

An AI agent receives a simple request: find the failed payment, check the customer record, ask a second service for its status, and explain what happened.

The first model call is inexpensive. The database lookup returns an incomplete result. The agent asks a tool again. A retry fails. A second agent is invoked to investigate. The original conversation, tool results, and growing scratchpad are sent back to the model on every turn.

Nothing looks alarming when viewed one call at a time.

The complete run is different. It may have consumed hundreds of thousands of input and output tokens, several tool calls, and more time than the business problem justified. The monthly provider invoice may tell you that the team spent more this month, but it may not tell you which run caused the increase, whether the cost produced a successful outcome, or where the loop should have stopped.

This is the problem TokenOps is trying to name.

In this article, I use TokenOps as an emerging label for observing, attributing, budgeting, enforcing, and improving token consumption across AI applications and agent workflows. It is not a universally defined standard. The useful idea is more concrete than the label: token usage needs an operational control loop, not just a billing report.

Microsoft's August 2026 article uses TokenOps as the name of a specific open-source system for run-scoped cost control; the broader operating practices discussed here are not that project's specification. For many hosted LLM APIs, tokens are a primary billing unit, although some products meter credits or action units instead. OpenTelemetry's GenAI conventions provide building blocks for tracing agent invocations, model calls, tool executions, and usage. These are useful starting points for the design below. [1][2]

Where TokenOps fits

The names around AI operations overlap, so it helps to define the boundary used in this article:

Discipline Primary concern
AIOps Applying AI to IT operations such as alert correlation, incident analysis, and remediation
LLMOps Deploying, evaluating, monitoring, and maintaining LLM applications and model workflows
FinOps Managing and allocating cloud or technology spend across teams and workloads
TokenOps Managing model usage at the agent-run level through attribution, optimization, budgets, and enforcement

These are complementary, not competing labels. TokenOps can be implemented as part of an LLMOps platform, reported through FinOps, and used by an AIOps workflow that calls an agent to investigate an incident.

TokenOps is not just cheaper prompts

The first response to rising token usage is usually prompt optimization: shorten the system prompt, remove redundant instructions, or choose a smaller model. Those actions can help, but they solve only one part of the problem.

An agent's consumption is a property of the entire workflow. It depends on:

Source of consumption Typical failure mode
Input context The same large history or retrieved documents are sent on every turn
Output generation The model produces long explanations when a structured answer would be enough
Retries A failed tool call causes the same expensive reasoning step to run again
Tool results A connector returns far more data than the agent needs
Delegation Multiple agents repeat overlapping research or validation
Model selection A high-cost model is used for classification or formatting
Unbounded loops The agent keeps trying because no shared run budget can stop it

The last two are architectural problems, not wording problems. A shorter prompt does not prevent a retry storm. A cheaper model does not make an infinite loop acceptable.

This is why TokenOps should be viewed as a companion to application engineering. It asks questions such as:

  • How much did this workflow spend before it produced a successful result?
  • Which user, team, repository, or business process owns that spend?
  • How much of it was productive work, and how much came from retries or duplicated context?
  • What should happen when the run reaches its budget?
  • Can the system stop the next model call before it is sent?

The invoice is too late

A monthly budget is useful for financial planning, but it is a weak runtime safety mechanism. It can notify a team that a limit was crossed; it usually cannot explain which live run should stop before the next call.

Per-request limits are also incomplete. An agent can remain under a limit on every individual call while exceeding the business value of the complete workflow. Ten calls that each cost a small amount can still be wasteful when the same failed step is repeated ten times.

The unit that needs a budget is often the run:

User request
  └── Agent run
      ├── Model call
      ├── Tool call
      ├── Model call
      ├── Retry
      └── Delegated agent
          └── Model call

For a multi-agent workflow, I would give the run one shared budget even when several workers or sub-agents participate. If each component receives its own independent allowance, the workflow can multiply its intended spend simply by multiplying the number of components.

That does not mean every run should have one fixed number. A short classification task, an incident investigation, and a code-generation workflow have different value and complexity. The budget should be attached to the workflow and business action, not copied blindly across every agent.

Four responsibilities of a practical TokenOps system

I would separate TokenOps into four responsibilities. They can start inside one application; they do not require four separate services.

1. Observe

Record the complete chain of work, not only the final answer. At minimum, a trace should connect:

  • The user request and workflow name.
  • The agent run ID.
  • Every model invocation and selected model.
  • Input and output token counts, plus cached and reasoning breakdowns when available.
  • Tool calls, results, failures, and retries.
  • Delegated agent runs.
  • Duration and time to first token where relevant.
  • The final business outcome.

OpenTelemetry's GenAI conventions include invoke_agent, chat, and execute_tool spans. They also define usage attributes such as gen_ai.usage.input_tokens and gen_ai.usage.output_tokens, alongside the gen_ai.client.token.usage metric described in the OpenTelemetry walkthrough. Using common names matters because it allows an engineering team to change dashboards and telemetry backends without redesigning the application's business events. [2]

The agent-span conventions are marked as being in development, so teams should pin the schema version they use and expect the conventions to evolve. [6]

Telemetry must be designed carefully. Prompts, tool results, and attachments may contain personal or confidential data. Full content capture should be opt-in, access-controlled, and subject to retention rules. TokenOps should improve operational visibility without turning the tracing system into an uncontrolled copy of the company's data.

2. Attribute

A provider invoice normally answers “how much did the organization spend?” It rarely answers “which business outcome consumed that spend?”

Every model call should inherit a stable run context, such as:

organization = finance
application = expense-assistant
workflow = disputed-payment-investigation
run_id = 01J...
initiating_user = user-1842
parent_run_id = optional-delegated-run

The exact fields depend on privacy and tenancy requirements. The principle is that cost and usage must be attributable at the same grain at which the team makes decisions.

For a business application, useful aggregates might include:

Question Useful measure
Is the workflow economically useful? Cost per successful task
Is the agent looping? Tokens and attempts per run
Is context too large? Input tokens by step and cache-hit ratio
Are tools causing waste? Tokens after failed or empty tool results
Which model is appropriate? Success rate and cost by model and task type
Which team owns the issue? Spend by application, workflow, and owner

Cost should be calculated from the actual model and billing arrangement, not inferred from token count alone. Price cached and noncached input at the applicable rates, and include relevant output, tool, and infrastructure charges. Microsoft distinguishes measured usage and cost estimates from the final invoice. [3]

Normalize usage at the provider adapter: cached input is commonly a subset of total input, and reasoning usage may already be included in total output. Do not add those breakdowns to the totals again. Missing usage means unknown, not zero, and must remain visible as an accounting gap. [3]

For this workflow, I would define cost per accepted outcome as total cost of all attempts for a defined task cohort divided by the number of accepted outcomes in that cohort. Include failed attempts and retries in the numerator; define acceptance using the business result rather than the agent's final message. With zero accepted outcomes, report the cost and zero completions rather than a misleading unit cost. If costs are incomplete, label the measure provisional.

3. Optimize

Optimization should begin with the largest source of avoidable work, not with a general instruction to “use fewer tokens.”

I would investigate in this order:

  1. Repeated calls caused by retries or a tool that returns an unusable result.
  2. Context that is re-sent but no longer relevant.
  3. Tool responses that should have been filtered, paginated, or summarized before reaching the model.
  4. A model whose capability exceeds the task's requirement.
  5. Delegated work that overlaps with work already completed.
  6. Output that is longer than the consuming application needs.

The correct optimization may be a database query, a schema change, a cache, a timeout, or a deterministic rule. It is not always a prompt rewrite.

There is also a quality tradeoff. A cheaper run that produces an incorrect approval, misses a security issue, or requires a human to redo the work is not necessarily more efficient. The meaningful metric is closer to cost per accepted outcome than cost per response.

4. Enforce

Observability tells us that a run is expensive. Enforcement determines what happens before the next expensive call.

A budget policy might contain:

{
  "workflow": "disputed-payment-investigation",
  "maxInputTokens": 180000,
  "maxOutputTokens": 30000,
  "maxModelCalls": 24,
  "maxToolCalls": 40,
  "maxElapsedTime": "00:05:00",
  "onExhausted": "save-and-escalate"
}

These are example controls, not universal values. A production policy should define whether cached tokens count toward the limit and whether delegated work shares the parent budget. Every retry needs its own admission against the remaining allowance; a provider error does not create extra budget. Compaction, summarization, and escalation messages that call a model consume budget too.

The enforcement point must be outside the model's control. A model-generated message saying “the budget is still available” is not a budget check. The service responsible for making the next model or tool call must consult the authoritative run ledger and make a deterministic allow, reduce, or stop decision.

Microsoft's Agent Framework and Agent Governance Toolkit overview describes tiered budget enforcement, including per-task limits, per-agent budgets, organization-wide caps, throttling, and a kill switch. That is an implementation direction, not proof that a package automatically solves every application's policy or billing problem. [4]

Token limits and dollar-denominated budgets answer different questions. A token limit can stop a run before it grows beyond its execution allowance; a financial budget governs spending across models, providers, and billing arrangements. A production system may need both. [7]

A small .NET enforcement boundary

A strict token cap needs more than a running total. Before dispatch, reserve an upper bound for the complete model call: bounded input plus a provider-enforced output limit, including reasoning tokens where applicable. An average-use estimate supports planning, not a hard guarantee.

Here is an in-memory, single-run accounting example. The host assigns a stable call ID before dispatch; the class tracks reservations and makes repeated settlement safe. It is not an SDK integration or a distributed ledger.

using System;
using System.Collections.Generic;

public sealed class RunBudget
{
    private sealed record Entry(long UpperBound, long? Actual = null);

    private readonly object _gate = new();
    private readonly long _limit;
    private readonly Dictionary<Guid, Entry> _calls = new();
    // Includes settled usage and outstanding upper-bound reservations.
    private decimal _committed;
    private bool _halted;

    public RunBudget(long limit)
    {
        if (limit <= 0)
            throw new ArgumentOutOfRangeException(nameof(limit));
        _limit = limit;
    }

    public bool TryReserve(Guid callId, long upperBound)
    {
        if (callId == Guid.Empty)
            throw new ArgumentException("A call ID is required.", nameof(callId));
        if (upperBound <= 0)
            throw new ArgumentOutOfRangeException(nameof(upperBound));

        lock (_gate)
        {
            if (_halted || _calls.ContainsKey(callId) ||
                _committed + upperBound > _limit)
                return false;

            _calls.Add(callId, new Entry(upperBound));
            _committed += upperBound;
            return true;
        }
    }

    public void Reconcile(Guid callId, long actualTokens)
    {
        if (actualTokens < 0)
            throw new ArgumentOutOfRangeException(nameof(actualTokens));

        lock (_gate)
        {
            if (!_calls.TryGetValue(callId, out var entry))
                throw new InvalidOperationException("Unknown reservation.");

            if (entry.Actual is long previous)
            {
                if (previous != actualTokens)
                    throw new InvalidOperationException("Conflicting settlement.");
                return; // Identical replay does not change the balance.
            }

            _calls[callId] = entry with { Actual = actualTokens };
            _committed += (decimal)actualTokens - entry.UpperBound;
            if (actualTokens > entry.UpperBound)
                _halted = true; // Record the overrun; deny future admissions.
        }
    }
}

If two calls reserve 60 and 40 tokens against a 100-token limit, a third reservation is refused until confirmed usage frees capacity. Settling the first call at 20 tokens twice frees 40 tokens only once. Negative bounds and negative usage are rejected. The decimal accumulator avoids overflowing a long addition while recording an unexpected overrun.

The guarantee is conditional: actual usage must fit the reserved bound, and every billable call must pass through this boundary. If a supposedly bounded call reports more usage, the class records it and halts future admissions; it cannot undo the already-incurred expense or cancel other in-flight calls. Production monitoring must flag that accounting breach.

The adapter must enforce the same output ceiling at the provider, bound all billable input, and normalize reported usage before settlement. Hidden provider work or an unenforceable reasoning/output ceiling means the policy is a best-effort guard, not a strict cap. This token-only example does not implement the earlier policy's separate input/output quotas, call limits, elapsed-time limit, tool charges, or dollar budget.

For multiple workers, persist the call ID, reservation, actual usage, and halt state in one authoritative store. Admission and settlement must each be atomic across all workers. A duplicate call ID must not dispatch another provider request. In production, return distinct rejection reasons rather than treating every false as budget exhaustion.

A timeout after dispatch, missing usage, cancellation, or a worker crash leaves the reservation outstanding. Do not settle it as zero or release it just because a timer expired. Reconcile from provider evidence or an explicit conservative accounting policy, and resolve an unknown outcome before blindly dispatching a replacement. An authoritative ledger must survive restarts; sampled traces are diagnostic evidence, not the balance used for enforcement.

Test the accounting before connecting a model

These are required acceptance cases for the proposed design, not claims that a deployed integration has passed them:

Case Required result
Concurrent admissions consume the remainder Atomic reservations; committed tokens stay within the cap when bounds hold
Same call ID is admitted twice No second reservation or provider dispatch
Identical settlement is replayed No second balance adjustment
Settlement has a different usage value Conflict surfaced; original settlement preserved
Negative values or arithmetic boundary values Invalid values rejected; no counter wraparound
Actual usage exceeds its reserved bound Actual usage recorded, breach alerted, future calls denied
Provider timeout or missing usage Reservation remains outstanding; outcome marked unknown
Worker restarts Reservation, halt state, and deduplication survive in the persistent ledger
Budget service is unavailable Strict-policy admission fails closed before dispatch
Provider output limit is reached Real adapter enforces the configured cap, including relevant reasoning usage

The in-memory class illustrates only the local accounting rules. Restart, cross-process concurrency, provider limits, and failure handling need tests against the actual store and model adapter.

Token budgets are also reliability controls

It is tempting to classify TokenOps as a finance feature. That is too narrow.

An agent that loops consumes time, increases latency, occupies worker capacity, and may repeat side effects. A budget exhaustion event is often an early warning of a broken tool contract, poor retrieval, an invalid state transition, or a missing stop condition.

OWASP lists Unbounded Consumption among the risks for LLM applications. The risk includes resource exhaustion, denial of service, and unexpected economic impact. A run-level token budget is one layer of defense, alongside rate limits, authentication, tool authorization, timeouts, and safe handling of external content. [5]

The response to exhaustion should be designed like any other application failure:

Exhaustion cause Safe response
Context too large Summarize, retrieve selectively, or ask for clarification
Repeated tool failure Stop, save the failure, and escalate with the failing dependency
Output too verbose Retry with a structured schema only if the remaining budget allows it
Parallel work exceeded allowance Cancel future work and preserve completed evidence
Business task is too complex Move to a human or asynchronous workflow

The user should see a truthful status such as “The investigation stopped after reaching its safety budget.” They should not receive “completed” merely because the model generated a final paragraph.

What TokenOps should not become

There are several ways to overcorrect.

First, do not reduce the entire discipline to a dashboard. A graph showing tokens by day is useful, but it does not stop a run, identify the owner, or explain whether the output was successful.

Second, do not optimize for minimum tokens at the expense of correctness. A short incorrect answer is not a successful optimization.

Third, do not make the model the only authority on its own usage. The provider response, application ledger, and enforced policy should determine the facts.

Fourth, do not assume that one global token limit is fair. Different workflows have different value, latency, and complexity. Policies should be explicit, reviewed, and tied to business outcomes.

Finally, do not present TokenOps as a mature industry standard. Today, it is a useful name for a set of practices that overlap with LLM observability, FinOps, reliability engineering, and agent governance. OpenTelemetry provides standard telemetry vocabulary; it does not define a complete TokenOps operating model. Microsoft provides examples of run-scoped controls; they are not a universal specification. This distinction is important because credible engineering writing should separate an emerging category from established standards.

A practical adoption path

I would introduce these controls in stages.

Stage 1: Make one workflow measurable

Choose a single agent workflow and add a stable run ID. Record model calls, token usage, tool calls, retries, latency, and the final business result. Do not begin by collecting every prompt and attachment. A dashboard should make these dimensions queryable by run, model, session, tool, latency, error, and owner. Microsoft's AI coding-agent monitoring guidance illustrates the value of exposing sessions, token usage, models, tool invocations, latency, and errors in one operational view. [8]

Stage 2: Establish ownership and baselines

Attribute usage to an application, workflow, team, and environment. Measure successful outcomes, not just total tokens. Establish a baseline for cost, latency, retries, and failure rate.

Stage 3: Add warnings and budgets

Set soft thresholds that expose unusual runs without interrupting users. Then add hard limits for the workflows where an unbounded run could create material cost, latency, or operational risk.

Stage 4: Make exhaustion recoverable

Persist the run state and the reason for stopping. Offer a safe next action: clarify the request, retry a specific dependency, continue asynchronously, or escalate to a person. A budget control that leaves no useful recovery path will be bypassed.

Stage 5: Optimize the expensive failure modes

Use the traces to fix repeated tool calls, oversized responses, poor retrieval, and unnecessary delegation. Re-evaluate success and cost after each change. Do not celebrate a lower token count until the accepted outcome remains stable.

The first dashboard is not the finish line. It is the evidence needed to decide where the system is wasting effort and where a stricter control is justified.

Final thoughts

AI agents introduce a new kind of operational unit: a workflow that can decide how many model calls, tool calls, retries, and delegated tasks it needs before it reaches an answer.

That flexibility is useful, but it makes request-level thinking insufficient. The organization needs to observe the complete run, attribute it to an owner and outcome, improve the waste, and enforce a limit before the next call is made.

Whether the industry ultimately keeps the name TokenOps is less important than adopting the discipline behind it.

An agent should not be judged only by whether it produced a convincing answer. In production, we also need to know what it cost, what it changed, what it tried, and whether the result justified the work.
