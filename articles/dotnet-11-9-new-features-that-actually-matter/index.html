.NET 11: 9 New Features That Actually Matter to Developers

.NET 11 has a long changelog. These are the changes that can actually affect the way we model domains, run async code, build APIs, query data, ship mobile apps, and reduce custom infrastructure.

By Islam Darawsheh August 21, 2026 12 min read

.NET 11 is still in preview, but by Preview 7 the direction of the release is already clear. There are dozens of runtime, SDK, library, ASP.NET Core, C#, EF Core, and .NET MAUI changes. Most application developers have a simpler question: which of them are likely to matter in real projects?

As of this writing, .NET 11 Preview 7 was released on August 11, 2026. Some of the features below arrived in earlier .NET 11 previews and continued evolving afterward, so this is not a “Preview 7 only” list. It is a practical selection of the features I would pay attention to before GA.

The filter for this article:

Not every new API deserves an architecture meeting. I picked changes that can simplify production code, alter performance characteristics, reduce dependencies, or open a genuinely useful capability.

1. C# 15 is getting union types and closed hierarchies

One of the most interesting C# 15 directions is the combination of union types and closed type hierarchies. A union models a value that can be one of a known set of types, while a closed hierarchy lets the compiler know the complete set of legal derived types.

public record Dog(string Name);
public record Cat(int Lives);

public union Pet(Dog, Cat);

Pet pet = new Cat(9);

if (pet is Cat { Lives: > 0 } cat)
{
    Console.WriteLine(cat.Lives);
}

This is useful anywhere we currently model “one of these known outcomes” with inheritance, wrapper classes, enum-plus-payload patterns, or custom result objects.

public closed record class Shape;

public record class Circle(double Radius) : Shape;
public record class Square(double Side) : Shape;

static double Area(Shape shape) => shape switch
{
    Circle(var r) => Math.PI * r * r,
    Square(var s) => s * s
};

Because the compiler knows the permitted derived types, exhaustive pattern matching becomes much more valuable. Preview 7 also advances System.Text.Json support for closed hierarchies, reducing some of the manual polymorphism configuration normally required.

I would not redesign a production domain around preview language features today, but I would absolutely experiment with them in result models, state machines, and bounded domain hierarchies.

2. Runtime async could change the cost model of async/await

C# normally implements async methods using compiler-generated state machines. .NET 11 is developing another path: runtime async, where the runtime can participate more directly in transforming and optimizing async methods.

public async Task<Order> GetOrderAsync(
    Guid id,
    CancellationToken cancellationToken)
{
    return await repository.GetAsync(id, cancellationToken);
}

The attractive part is that application code stays idiomatic. There is no special syntax to learn. The potential benefit comes from making existing async/await code cheaper through runtime optimization, tiered compilation, and improved tail-await behavior.

That can matter in high-throughput APIs, workers, messaging systems, and I/O-heavy services where small per-call improvements compound across millions of operations.

3. System.Diagnostics.Process is becoming much easier to manage safely

Starting a process is simple. Managing one correctly is not. Tooling code often ends up dealing with stdout/stderr coordination, child lifetimes, process trees, and platform-specific cleanup.

.NET 11 expands the System.Diagnostics.Process surface with capabilities such as parent-exit cleanup and broader process-start controls.

var startInfo = new ProcessStartInfo("my-helper")
{
    KillOnParentExit = true
};

Process.Start(startInfo);

This is especially relevant for CLI tools, IDE integrations, local orchestration, test runners, desktop applications, build tooling, and systems that launch helper workers.

4. HttpClient can compress request bodies directly

Response compression is common. Request compression has historically required more custom plumbing. .NET 11 adds request-content wrappers directly to System.Net.Http, including gzip, Brotli, and Zstandard.

using var request = new HttpRequestMessage(
    HttpMethod.Post,
    "https://example.com/api")
{
    Content = new ZstandardCompressedContent(
        new StringContent(json),
        CompressionLevel.Optimal)
};

using HttpResponseMessage response =
    await client.SendAsync(request);

This can be useful for telemetry ingestion, bulk APIs, synchronization endpoints, large JSON payloads, and device-to-server uploads. Request compression remains opt-in, so the server still needs to support the encoding you choose.

5. LINQ finally gets FullJoin

This one looks small until you remember how much boilerplate a full outer join used to require. .NET 11 adds FullJoin across LINQ surfaces so matching rows and unmatched rows from both sides can be expressed directly.

var rows = catalog.FullJoin(
    sales,
    product => product.Sku,
    sale => sale.Sku,
    (product, sale) => new
    {
        Sku = product?.Sku ?? sale!.Sku,
        ProductName = product?.Name ?? "(missing)",
        Quantity = sale?.Quantity ?? 0
    });

Think reconciliation: expected vs. actual, source vs. destination, configured vs. discovered, previous snapshot vs. current snapshot, inventory vs. transactions.

6. Password-protected ZIP files no longer require a third-party library

System.IO.Compression in .NET 11 can read and write password-protected ZIP entries, including AES-based encryption options.

using var archive =
    ZipFile.Open("export.zip", ZipArchiveMode.Create);

ZipArchiveEntry entry = archive.CreateEntry(
    "report.txt",
    password: password,
    encryptionMethod: ZipEncryptionMethod.Aes256);

using Stream stream = entry.Open(password);
using var writer = new StreamWriter(stream);
writer.WriteLine("Encrypted contents");

That removes a common reason to add another dependency for enterprise exports, partner integrations, encrypted reports, and archive workflows.

Of course, built-in encryption does not make hard-coded passwords acceptable. Secret handling is still an application-security decision.

7. ASP.NET Core and Blazor are getting more production-oriented

.NET 11 continues the trend of making Blazor and ASP.NET Core operationally stronger rather than merely adding UI features. Preview 7 includes work around inactive Blazor circuits, SSR caching, validation, authentication refresh, authorization metadata, and OpenAPI.

The inactive-circuit work is especially interesting for Blazor Server. A user can leave a tab open for hours while the server continues to own circuit state. More intelligent pausing gives the runtime a better way to trade resource usage against user continuity.

For Blazor SSR, caching and validation improvements also remove areas where applications previously needed custom infrastructure.

8. EF Core is bringing vector search closer to normal application data access

Vector search is increasingly becoming a normal database capability rather than something that automatically requires a dedicated vector database. During the .NET 11 cycle, EF Core has been adding support around SQL Server vector capabilities and approximate vector search.

Relational data
    +
Vector embeddings
    +
EF Core query model

This matters for semantic search, recommendations, document retrieval, RAG systems, similarity matching, and AI-assisted discovery.

It does not mean specialized vector databases are obsolete. They can still win on indexing models, scale, filtering, or operations. But if an enterprise system already lives on SQL Server, keeping relational and vector data in one persistence boundary can eliminate a lot of synchronization complexity.

9. .NET MAUI and NativeAOT keep improving the development and startup story

.NET MAUI in .NET 11 is getting developer-experience and runtime-oriented improvements, including work around passkeys, XAML Incremental Hot Reload, Shell routing, AOT-safe binding patterns, and faster device workflows.

At the SDK level, .NET 11 also keeps pushing NativeAOT deeper into normal tooling. The broader signal is more important than any one benchmark:

NativeAOT is becoming less of a specialized deployment trick and more of a normal optimization path across the .NET ecosystem.

For MAUI, trimming and AOT safety affect startup, binary size, and linker compatibility. For command-line tools, NativeAOT can drastically reduce startup overhead. For backend services, it continues to improve startup and deployment density where the trade-offs fit.

What I would actually experiment with today

I would not migrate a production system just to chase preview features. I would create a lab branch and test the areas that map to real problems in the codebase.

Backend and API teams

  • HTTP request compression.
  • Runtime async benchmarks against your own hot paths.
  • FullJoin for reconciliation code.
  • New Process APIs if you launch helpers or workers.
  • EF Core vector capabilities if semantic search is on your roadmap.

C# language design

  • Union types.
  • Closed hierarchies.
  • Exhaustive pattern matching.
  • JSON polymorphism over closed models.

MAUI teams

  • XAML Incremental Hot Reload.
  • AOT-safe bindings.
  • Shell navigation improvements.
  • Passkeys.
  • Real-device workflow changes.

The bigger .NET 11 theme

The most interesting part of .NET 11 is not a single headline feature. The release attacks friction at several layers at once:

C# language
    ↓
safer domain modeling

BCL
    ↓
less custom infrastructure

Runtime
    ↓
cheaper async + better AOT

ASP.NET Core
    ↓
better production behavior

EF Core
    ↓
more capable data access

MAUI
    ↓
better device development + AOT safety

.NET does not need a completely new programming model every year. A mature platform gets better by making common paths safer, faster, and easier while exposing more control for advanced workloads. So far, .NET 11 looks like that kind of release.

Should you upgrade now?

For production systems: not yet. .NET 11 is still in preview.

For experiments, compatibility testing, internal prototypes, and library validation: yes. The earlier you test, the more time you have to find breaking changes, analyzer differences, trimming issues, library incompatibilities, and performance surprises before GA.
