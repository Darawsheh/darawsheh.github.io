Pagination in EF Core: Page Numbers vs. Cursors Is a Product Decision

Stop choosing pagination before you know what the UI needs. A screen that must show “Page 3 of 47” asks the database a different question from a feed that only needs “Load more.”

By Islam Darawsheh August 11, 2026 13 min read

Pagination is often introduced as a database technique: choose Skip/Take or choose a cursor. I think that starts one step too late. The first question belongs to the product and the UI: does the user need numbered random access and an exact page count, or only a reliable way to continue through the result set?

Those two interfaces look similar on screen, but they create different API contracts and different database work.

The principle for this article:

Choose the pagination model from the navigation requirement first. Then design the EF Core query, indexes, and API contract around that requirement.

Keep two UIs in mind

We will use the same Orders data throughout the article, but with two different UI requirements.

Scenario A — numbered pages

The UI shows total results, Page 3 of 47, page numbers, and allows a direct jump to another page.

Scenario B — sequential navigation

The UI shows Load more or Next/Previous. It does not need the exact number of pages or results.

This distinction matters more than whether somebody calls one technique “best practice.”

Scenario A: the UI needs to know there are 47 pages

A traditional administrative grid might show:

Orders

1  2  3  4  5  ...  47
Page 3 of 47
934 orders

The API cannot truthfully return “47 pages” unless it knows how many matching rows exist. That means the pagination contract normally includes count metadata:

public sealed record PagedResponse<T>(
    IReadOnlyList<T> Items,
    int Page,
    int PageSize,
    long TotalCount,
    long TotalPages);

Assume the list is filtered to visible orders. Define that filter once so the count and page query do not accidentally drift apart:

IQueryable<Order> filteredOrders = db.Orders
    .Where(x => x.Status != OrderStatus.Deleted);

var totalCount = await filteredOrders
    .LongCountAsync(cancellationToken);

var totalPages = (long)Math.Ceiling(
    totalCount / (double)pageSize);

var offset = checked((page - 1) * pageSize);

var items = await filteredOrders
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id)
    .Skip(offset)
    .Take(pageSize)
    .Select(x => new OrderSummaryResponse(
        x.Id,
        x.CreatedAt,
        x.Status,
        x.Total))
    .ToListAsync(cancellationToken);

return new PagedResponse<OrderSummaryResponse>(
    items,
    page,
    pageSize,
    totalCount,
    totalPages);

There are usually two database operations here:

COUNT matching rows
+
fetch one ordered page using OFFSET

That is not a criticism. It is the cost of the product requirement. If the user genuinely needs 934 results, 47 pages, and a direct jump to page 47, the API needs enough information to support those features.

Do not oversimplify COUNT(*):

An exact count is not automatically expensive on every database or every query. Its cost depends on the provider, filters, joins, indexes, statistics, and execution plan. Treat it as database work to measure, not as something that is either always free or always slow.

The hidden consistency question in “Page 3 of 47”

The count query and page query are two separate executions. Imagine this sequence:

COUNT(*) returns 934

-- another transaction inserts an order --

SELECT page 3 returns data from a 935-row state

For many administrative screens, that small difference is completely acceptable. The user asked for a useful view of changing operational data, not a frozen mathematical snapshot.

If the product requires the total count and page rows to represent the exact same database snapshot, that becomes a separate consistency requirement. The solution depends on the database provider and transaction/isolation semantics, and it may add cost or contention. Do not silently upgrade every paged endpoint to a stronger isolation level just because two queries are involved.

This is a recurring theme: the UI requirement should drive the data guarantee, not the other way around.

Offset pagination is not wrong

For Scenario A, Skip and Take are often the most natural API model:

GET /orders?page=47&pageSize=20
var items = await filteredOrders
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id)
    .Skip((page - 1) * pageSize)
    .Take(pageSize)
    .Select(x => new OrderSummaryResponse(
        x.Id,
        x.CreatedAt,
        x.Status,
        x.Total))
    .ToListAsync(cancellationToken);

It supports something keyset pagination does not naturally provide: random page access. If a user clicks page 47, offset pagination can express that request directly.

Microsoft's EF Core pagination guidance makes the same trade-off explicit: keyset pagination is recommended for next/previous navigation, while random access to arbitrary pages generally requires offsets. A hybrid design is also possible when a product needs both behaviors.

What a large offset actually asks the database to do

This is where wording matters. Consider:

.Skip(100_000)
.Take(20)

It would be inaccurate to say that every database always reads 100,000 complete table rows and throws them away. Optimizers, indexes, covering indexes, storage engines, and execution plans can change the amount and type of work substantially.

The more accurate statement is:

With offset pagination, the database must still account for the rows preceding the requested offset in the ordered result. A good index and optimizer can make that work cheaper, but the cost generally grows as the offset grows.

Microsoft's EF Core documentation states that the database still has to process the entries before the requested offset even though they are not returned. PostgreSQL's documentation says skipped OFFSET rows still have to be computed inside the server and warns that a large offset may be inefficient.

MySQL is a good reminder not to overgeneralize the physical implementation: its documentation describes several LIMIT optimizations, including choosing indexes in some cases and stopping sorting early depending on the query. The exact execution plan is provider-specific.

Provider matters:

Do not publish performance claims from LINQ alone. For important queries, inspect the SQL and execution plan on the actual database engine you run in production.

Scenario B: the UI only needs to know whether more data exists

Now change the product requirement. The screen looks like this:

Orders

[ Order ]
[ Order ]
[ Order ]

Load more

The UI does not care whether there are 934 records or 935. It does not need to know whether this would be called page 3 or page 47. It asks a much smaller question:

Give me the next batch after the last item I already saw. Also tell me whether more data exists.

That requirement fits keyset, or seek, pagination naturally.

Keyset pagination gives the database a boundary

Assume the ordering is:

.OrderByDescending(x => x.CreatedAt)
.ThenByDescending(x => x.Id)

The last item the client received had:

CreatedAt = 2026-08-11T05:42:31Z
Id        = 892731

The next query does not say “skip 100,000.” It says “continue after this known boundary”:

IQueryable<Order> query = db.Orders
    .Where(x => x.Status != OrderStatus.Deleted);

if (cursor is not null)
{
    query = query.Where(x =>
        x.CreatedAt < cursor.CreatedAt ||
        (x.CreatedAt == cursor.CreatedAt &&
         x.Id < cursor.Id));
}

var rows = await query
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id)
    .Take(pageSize + 1)
    .Select(x => new OrderSummaryResponse(
        x.Id,
        x.CreatedAt,
        x.Status,
        x.Total))
    .ToListAsync(cancellationToken);

With an appropriate index, the engine can use the boundary values as a seek/range condition rather than repeatedly locating a deeper numeric offset. That is why Microsoft recommends keyset pagination when the UI primarily moves sequentially through results.

Fetch one extra row instead of counting everything

Scenario B still needs to know whether the “Load more” button should exist. It does not need an exact total count.

So request one extra row:

var requestedSize = Math.Clamp(pageSize, 1, 100);

var rows = await query
    .OrderByDescending(x => x.CreatedAt)
    .ThenByDescending(x => x.Id)
    .Take(requestedSize + 1)
    .Select(x => new OrderSummaryResponse(
        x.Id,
        x.CreatedAt,
        x.Status,
        x.Total))
    .ToListAsync(cancellationToken);

var hasMore = rows.Count > requestedSize;

var items = rows
    .Take(requestedSize)
    .ToArray();

If 26 rows come back for a requested size of 25, the API knows there is at least one more item. The 26th row is not returned as part of the page.

Notice what we deliberately did not ask:

How many rows exist in total?
How many pages exist?
What page number is this?

The UI did not need those answers, so the API did not manufacture requirements for itself.

The most important rule is deterministic ordering

This query is not enough:

.OrderByDescending(x => x.CreatedAt)

Two orders can have the same timestamp. If the page boundary lands between them, their relative order is not guaranteed by CreatedAt alone.

Microsoft's EF Core pagination documentation explicitly warns that pagination ordering must be fully unique. The same idea appears in MySQL and PostgreSQL documentation: when the ordering is not deterministic, different query plans or page requests can produce unpredictable subsets.

Use a tie-breaker:

.OrderByDescending(x => x.CreatedAt)
.ThenByDescending(x => x.Id)

If Id is unique, the pair (CreatedAt, Id) creates a fully deterministic order.

This matters for both offset and keyset pagination. It is not a cursor-only concern.

Why this example uses a numeric ID

In an earlier .NET 10 article I used Guid.CreateVersion7() for UUIDv7 identifiers. That does not mean I would blindly use UUID comparison as a pagination tie-breaker across every relational database.

Keyset pagination depends on the database provider's ordering and storage semantics. UUID behavior can differ between providers and native database types. For this example I deliberately use a long Id so the pagination concept is not mixed with provider-specific UUID ordering.

If your production key is UUIDv7, verify how your actual provider stores, compares, and indexes it before relying on its ordering in a seek predicate.

The index belongs in the pagination design

If the query consistently orders by:

CreatedAt DESC, Id DESC

then a matching composite index is a natural candidate:

builder.HasIndex(x => new
    {
        x.CreatedAt,
        x.Id
    })
    .IsDescending();

Microsoft's EF Core index documentation notes that composite index sort order can be important for query performance and generally should correspond to the query's ORDER BY.

That still does not mean “copy this index everywhere.” Filters, included columns, data distribution, provider behavior, and competing write costs all matter.

Pagination design and index design belong in the same conversation.

Make the cursor an API detail, not a database contract

I do not want the client to construct CreatedAt and Id boundaries manually. The response can expose an opaque cursor:

public sealed record CursorPage<T>(
    IReadOnlyList<T> Items,
    string? NextCursor,
    bool HasMore);

A small cursor payload can be encoded as Base64Url:

using System.Text.Json;
using Microsoft.AspNetCore.WebUtilities;

public sealed record OrderCursor(
    DateTimeOffset CreatedAt,
    long Id);

public static class CursorCodec
{
    private static readonly JsonSerializerOptions JsonOptions =
        new(JsonSerializerDefaults.Web);

    public static string Encode(OrderCursor cursor)
    {
        var bytes = JsonSerializer.SerializeToUtf8Bytes(
            cursor,
            JsonOptions);

        return WebEncoders.Base64UrlEncode(bytes);
    }

    public static bool TryDecode(
        string? value,
        out OrderCursor? cursor)
    {
        cursor = null;

        if (string.IsNullOrWhiteSpace(value))
            return false;

        try
        {
            var bytes = WebEncoders.Base64UrlDecode(value);
            cursor = JsonSerializer.Deserialize<OrderCursor>(
                bytes,
                JsonOptions);

            return cursor is not null;
        }
        catch (FormatException)
        {
            return false;
        }
        catch (JsonException)
        {
            return false;
        }
    }
}

The client receives something like:

GET /orders?limit=25&cursor=eyJ...

It does not need to know which database columns define the seek boundary.

Opaque is not secret:

Base64Url is encoding, not encryption, and it does not prevent tampering. Decode and validate every cursor as untrusted input. If integrity or confidentiality matters, use an authenticated protection mechanism appropriate to the application.

Also keep authorization and tenant filters server-side. A cursor may describe position, but it must never become authority to read another user's or tenant's data.

Numbered pages and cursors answer different questions

Numbered / offset

Best fit: exact totals, page numbers, direct jumps, administrative grids, reports.

Trade-off: deep offsets can require increasing work; exact totals usually require a count query.

Cursor / keyset

Best fit: feeds, timelines, logs, activity history, infinite scroll, sequential navigation.

Trade-off: no natural direct jump to arbitrary page 47; cursor design is part of the API.

The practical comparison looks like this:

Numbered pages

Next/Previous: yes

Exact total: natural

“Page 3 of 47”: natural

Jump to page 47: natural

Deep sequential navigation: can become costly

Cursor pages

Next: natural

Exact total: usually omitted

“Page 3 of 47”: not natural

Jump to page 47: not natural

Deep sequential navigation: strong fit

What about Previous?

Forward keyset pagination is the simplest form. A real UI may also need Previous. That is possible, but it is not achieved by pretending the cursor is a page number.

A typical implementation uses the opposite seek predicate and sort direction to fetch the preceding batch, then normalizes the returned order for the client. The exact contract depends on whether you expose one cursor, separate nextCursor/previousCursor values, or a navigation link model.

The important point is that “Next/Previous” is still sequential navigation. It does not imply that the API must know the total page count.

Cap the page size in both scenarios

Neither offset nor cursor pagination should let the caller casually request an unbounded result set:

const int DefaultPageSize = 25;
const int MaxPageSize = 100;

var pageSize = Math.Clamp(
    requestedPageSize ?? DefaultPageSize,
    1,
    MaxPageSize);

Pagination is not just a UI concern. It is also a resource-control boundary for database work, serialization, network transfer, and application memory.

Project only what the list needs

Both scenarios should avoid loading entire entity graphs when the list needs only a summary:

.Select(x => new OrderSummaryResponse(
    x.Id,
    x.CreatedAt,
    x.Status,
    x.Total))

Microsoft's EF Core performance guidance recommends projecting only required properties and limiting result-set size. Pagination does not help much if each row still materializes a large graph the UI never uses.

This also continues a rule from the previous article: your EF Core entity does not need to become your public API response.

Test the page boundary, not only the row count

A useful pagination test creates values that make ordering ambiguous unless the tie-breaker is correct:

10:00:00 / 104
10:00:00 / 103
10:00:00 / 102
10:00:00 / 101

Fetch the first batch, then the next batch, and verify that the pages do not overlap:

firstPage.Items
    .Select(x => x.Id)
    .Intersect(secondPage.Items.Select(x => x.Id))
    .Should()
    .BeEmpty();

Also test inserts and deletes between requests if your product depends on a specific navigation behavior under concurrent changes.

Scope matters: this article is about relational EF Core pagination

The discussion above targets relational database providers. Microsoft explicitly notes that Azure Cosmos DB has its own pagination mechanism. Other distributed or non-relational data stores may expose continuation tokens or provider-specific semantics that should be used instead of importing relational assumptions.

Even among relational engines, SQL syntax and physical execution differ. Keep the conceptual trade-off, but verify the implementation on your provider.

The design I would ship

For a back-office grid where users need an exact result count and direct page jumps:

UI needs total pages
        |
        v
apply identical filters
        |
        +----> COUNT matching rows
        |
        v
ORDER BY fully unique key
        |
        v
OFFSET + page size
        |
        v
project response
        |
        v
return Page / TotalCount / TotalPages

For a large operational feed where the UI only needs to continue:

UI needs next batch
        |
        v
validate + decode cursor
        |
        v
apply authorization and filters
        |
        v
seek after cursor boundary
        |
        v
ORDER BY fully unique key
        |
        v
matching composite index
        |
        v
TAKE pageSize + 1
        |
        v
project response
        |
        v
return Items / NextCursor / HasMore

The rule is not “never use Skip”

If you leave this article remembering only “keyset good, offset bad,” then the article failed.

Use offset pagination when numbered random access and exact page metadata are genuinely valuable to the user.

Use keyset pagination when sequential navigation, changing data, and deep result sets matter more than arbitrary page numbers.

And regardless of which one you choose:

  • Make ordering fully deterministic.
  • Design the supporting indexes.
  • Cap page size.
  • Project only required data.
  • Keep authorization independent of cursor input.
  • Measure important queries on the real provider.
  • Test behavior around page boundaries.
Pagination is an API and product decision before it is an EF Core decision.

The UI that displays “Page 3 of 47” is asking for more information than the UI that displays “Load more.” Once that distinction is explicit, the database design becomes much easier to reason about.
