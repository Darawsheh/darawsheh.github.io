Stop Exposing EF Core Entities from Your .NET 10 APIs

Your persistence model, request model, and public response contract solve different problems. Reusing one type for all three saves a few lines today and creates coupling, security risk, and versioning friction tomorrow.

By Islam Darawsheh August 10, 2026 12 min read

One of the easiest ASP.NET Core APIs to build is also one of the easiest to regret: query an EF Core entity, return it directly, and let JSON serialization define the contract.

It feels efficient. There is no mapping code, no response model, and no apparent duplication. But the shortcut quietly makes your database-facing model part of your public HTTP surface.

The principle for this article:

An EF Core entity is a persistence/domain concern. An HTTP request is client input. An HTTP response is a public contract. They can share concepts without sharing the same type.

The convenient endpoint that creates the problem

Imagine an order entity that contains everything the application needs internally:

public sealed class Order
{
    public Guid Id { get; set; }
    public string Number { get; set; } = string.Empty;
    public OrderStatus Status { get; set; }
    public decimal TotalAmount { get; set; }
    public string Currency { get; set; } = string.Empty;

    public string? InternalRiskNote { get; set; }
    public byte[] RowVersion { get; set; } = [];

    public List<OrderItem> Items { get; set; } = [];
}

Then the API returns it directly:

static async Task<Results<Ok<Order>, NotFound>> GetOrder(
    Guid id,
    OrderingDbContext db,
    CancellationToken cancellationToken)
{
    var order = await db.Orders
        .Include(x => x.Items)
        .SingleOrDefaultAsync(
            x => x.Id == id,
            cancellationToken);

    return order is null
        ? TypedResults.NotFound()
        : TypedResults.Ok(order);
}

The endpoint compiles, and the response is strongly typed. The problem is not syntax. The problem is that Order now has two owners: EF Core and external clients.

Add InternalRiskNote for an operations workflow and it may suddenly appear in JSON. Add a concurrency token and it becomes part of the wire shape. Add a navigation property and you can change payload size, serialization behavior, and generated OpenAPI without intentionally changing the API.

Persistence shape is not contract shape

EF Core entities are designed around persistence, relationships, change tracking, invariants, and database mapping. API contracts are designed around what a caller is allowed to send or needs to receive.

Those goals overlap sometimes, but not enough to make the types interchangeable.

EF Core entity

Persistence identity, relationships, concurrency, domain state, database mapping.

Request contract

Only data the caller is allowed to provide for a specific operation.

Response contract

Stable, intentional data the API promises to return.

Application model

Data needed to execute a use case, independent of transport details.

Microsoft's .NET architecture guidance makes the same distinction from another direction: commands are DTO-like messages that contain exactly the information needed to perform an operation, not the entire domain object.

Input models are a security boundary

The output-side problem is accidental exposure. The input-side problem is often worse: overposting.

This is the kind of update endpoint I do not want:

app.MapPut(
    "/orders/{id:guid}",
    async (
        Guid id,
        Order request,
        OrderingDbContext db,
        CancellationToken cancellationToken) =>
    {
        if (id != request.Id)
            return Results.BadRequest();

        db.Orders.Update(request);
        await db.SaveChangesAsync(cancellationToken);

        return Results.NoContent();
    });

The caller is now posting an Order, which contains fields such as status, totals, internal notes, and concurrency data. Even if validation currently prevents some bad states, the contract communicates the wrong authority: it suggests the client may submit the persistence model.

Microsoft's ASP.NET Core model-binding guidance explicitly recommends dedicated view/input models as the protection mechanism for overposting rather than relying on broad entity binding.

A focused request says what the caller is actually allowed to change:

public sealed record ChangeShippingAddressRequest(
    string AddressLine1,
    string City,
    string CountryCode);

That type is not duplication. It is an allow-list expressed in code.

Name contracts by intent, not by habit

I avoid a generic type named OrderDto when the same concept crosses the API in different directions. The name hides an important design question: DTO for what?

public sealed record CreateOrderRequest(
    Guid CustomerId,
    IReadOnlyList<CreateOrderLineRequest> Items);

public sealed record OrderResponse(
    Guid Id,
    string Number,
    OrderStatus Status,
    decimal TotalAmount,
    string Currency,
    IReadOnlyList<OrderItemResponse> Items);

public sealed record OrderItemResponse(
    Guid ProductId,
    string ProductName,
    int Quantity,
    decimal UnitPrice);

CreateOrderRequest describes an operation. OrderResponse describes a representation. They can evolve independently because they are different contracts.

Design choice:

I prefer explicit request/response names over one reusable *Dto type. That is a design preference, not a Microsoft API requirement. The important requirement is keeping authority and contract shape explicit.

Project directly to the response contract

Once response types are explicit, EF Core can project directly into them instead of materializing a full entity graph first.

static async Task<Results<Ok<OrderResponse>, NotFound>> GetOrder(
    Guid id,
    OrderingDbContext db,
    CancellationToken cancellationToken)
{
    var response = await db.Orders
        .Where(x => x.Id == id)
        .Select(x => new OrderResponse(
            x.Id,
            x.Number,
            x.Status,
            x.TotalAmount,
            x.Currency,
            x.Items
                .OrderBy(item => item.Id)
                .Select(item => new OrderItemResponse(
                    item.ProductId,
                    item.ProductName,
                    item.Quantity,
                    item.UnitPrice))
                .ToList()))
        .SingleOrDefaultAsync(cancellationToken);

    return response is null
        ? TypedResults.NotFound()
        : TypedResults.Ok(response);
}

This does more than prevent data leakage. EF Core's performance guidance recommends projecting only the properties a query actually needs. A projection allows the provider to select the required columns instead of loading an entire entity merely to discard fields during mapping.

A useful EF Core nuance: AsNoTracking is not a ritual

You may notice that the projection above does not call AsNoTracking(). That is intentional.

EF Core tracks entity instances by default, and AsNoTracking() is useful for read-only queries that return entities. But Microsoft's tracking documentation also states that when a projection contains no entity instances, there is nothing for the context to track.

Because OrderResponse and OrderItemResponse are plain contract types, the query above does not materialize Order or OrderItem entities into the result.

// Useful when the result is an entity:
var order = await db.Orders
    .AsNoTracking()
    .SingleOrDefaultAsync(
        x => x.Id == id,
        cancellationToken);

// Not required just for ceremony when the result
// contains no entity instances:
var response = await db.Orders
    .Where(x => x.Id == id)
    .Select(x => new OrderSummaryResponse(
        x.Id,
        x.Number,
        x.TotalAmount))
    .SingleOrDefaultAsync(cancellationToken);

The larger rule is more useful than memorizing one method call: understand what EF Core is materializing and whether those instances need change tracking.

TypedResults make the contract visible to code and OpenAPI

For Minimal APIs, Microsoft documents TypedResults as the strongly typed alternative to Results. The concrete result types improve testability and provide response metadata that can describe the endpoint to OpenAPI.

static async Task<Results<Ok<OrderResponse>, NotFound>> GetOrder(
    Guid id,
    OrderingDbContext db,
    CancellationToken cancellationToken)
{
    var response = await LoadOrderResponse(
        id,
        db,
        cancellationToken);

    return response is null
        ? TypedResults.NotFound()
        : TypedResults.Ok(response);
}

That method signature is useful documentation by itself: a successful response contains OrderResponse; the other declared outcome is 404 Not Found.

Using a typed result does not fix a bad model, though. Ok<Order> is still a strongly typed leak. The important decision is the type inside the result.

Errors are contracts too

Do not carefully design successful responses and then return random anonymous error objects from each endpoint.

ASP.NET Core provides ProblemDetails support for machine-readable HTTP API errors. In .NET 10, the default problem-details service can be registered with AddProblemDetails().

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddProblemDetails();

var app = builder.Build();

app.UseExceptionHandler();
app.UseStatusCodePages();

For an explicit business conflict, a Minimal API can return a typed problem result:

static Results<NoContent, ProblemHttpResult> RejectIfLocked(
    Order order)
{
    if (!order.IsLocked)
        return TypedResults.NoContent();

    return TypedResults.Problem(
        statusCode: StatusCodes.Status409Conflict,
        title: "Order is locked",
        detail: "The shipping address can no longer be changed.");
}

Microsoft's error-handling guidance also carries an important security warning: do not send sensitive exception details to clients. A consistent error contract is not an excuse to serialize internal failures.

Do not map after loading more than you need

A response model alone does not guarantee an efficient query. This still loads the entity graph first:

var order = await db.Orders
    .Include(x => x.Items)
    .SingleAsync(x => x.Id == id, cancellationToken);

var response = new OrderResponse(
    order.Id,
    order.Number,
    order.Status,
    order.TotalAmount,
    order.Currency,
    order.Items
        .Select(item => new OrderItemResponse(
            item.ProductId,
            item.ProductName,
            item.Quantity,
            item.UnitPrice))
        .ToList());

That can be correct when the domain entity itself is required for behavior. But for a read-only query whose final purpose is an API representation, direct projection usually communicates intent better and can reduce transferred data.

This is where I prefer manual LINQ projection for important API queries. A mapping library can be useful when it meaningfully reduces repetitive mapping, but it should not hide the database query shape or turn contract design into convention magic.

Separate read contracts from write models

There is another architectural benefit: read and write paths stop fighting over the same object shape.

A write use case may need:

  • A customer identifier.
  • Product identifiers and quantities.
  • A concurrency token.
  • No product description at all.

A read response may need:

  • Formatted product names.
  • Calculated totals.
  • Display status.
  • Links or presentation-friendly values.

Trying to make one entity satisfy persistence, commands, queries, and public JSON usually produces a type that is convenient for none of them.

Contract stability becomes intentional

Once the API returns explicit contracts, internal changes stop becoming accidental API changes.

Add an internal field

It stays internal until you deliberately add it to a response contract.

Rename a database column

The public JSON name does not need to change with persistence mapping.

Split an entity

The API can preserve one response shape while persistence evolves underneath.

Version a public field

The change is visible in a contract diff rather than hidden inside an entity refactor.

This is not about creating a DTO for every class in the solution. It is about treating a public boundary as something you design rather than something serialization discovers.

What I would standardize on a .NET 10 API

  • Dedicated request types per operation.
  • Dedicated response types per public representation.
  • Direct EF Core projection for read-only API queries.
  • TypedResults where their type metadata adds value.
  • ProblemDetails for consistent HTTP error contracts.
  • Domain/entities kept free to evolve for internal needs.
  • Contract tests around important public response shapes.

What I would not standardize

  • A mandatory *Dto for every internal type.
  • AsNoTracking() added blindly to every projection.
  • AutoMapper merely to avoid three explicit assignments.
  • EF entities annotated until they double as API schemas.
  • One request/response model reused across unrelated operations.
The goal is not more models. The goal is fewer accidental contracts.

An EF Core entity can be a good domain or persistence model and still be the wrong HTTP model. In a maintainable .NET API, that is not duplication to eliminate. It is a boundary worth keeping explicit.
