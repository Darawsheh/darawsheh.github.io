You Patched the Server. Did You Patch Your .NET App?

Updating the server is only part of runtime patching. Verify the artifact, container image, and process that actually run your application.

By Islam Darawsheh October 26, 2026 10 min read

Consider a server that has just received a .NET security update. The installation succeeded, the application responds, and a terminal lists the new runtime.

The service on that server could still be running with the old one.

It might include its own runtime. It might live inside an image built last month. Or its process might have started before the update and never restarted.

To verify a .NET runtime patch, you need to connect the update to the deployed application and its running process.

Why this matters now

On October 25, Microsoft released out-of-band security updates for .NET 8, 9, and 10, alongside .NET 11 RC3. The announcement covers a Brotli decoder vulnerability and a Linux tarball ownership issue, with different applicability conditions. It explicitly calls for different update actions for framework-dependent apps, self-contained apps, and containers. [1]

For that release, the listed updates are:

Release line October 25 update
.NET 8 8.0.33
.NET 9 9.0.22
.NET 10 10.0.14
.NET 11 preview RC3

These are runtime release versions, not SDK version numbers. Check the current Microsoft advisory before using them as an operational target. For the Brotli issue, exposure depends on processing Brotli-compressed input; ASP.NET Core request decompression and HttpClient automatic response decompression are not enabled by default. [1]

The question here is how to get an applicable fix into the application that is actually running.

First, find out who supplies the runtime

The two main publishing modes put the runtime in different places. A framework-dependent deployment uses a compatible shared runtime in its execution environment. A self-contained deployment ships the required runtime with the application. [2]

Deployment Where the runtime comes from Where to apply a runtime fix
Framework-dependent app on a server A shared installation available to the app host Update the appropriate shared runtime, restart the app, and verify selection
Self-contained app The published application artifact Publish a replacement containing the fixed runtime and redeploy it
Framework-dependent app in a container Usually the final image's shared runtime Rebuild using the updated runtime image and replace the deployed containers
Self-contained app in a container The application copied into the image Republish the app with the fix, rebuild the image, and replace deployed containers

A container can use either publishing mode. For the normal image-based deployments discussed here, installing .NET on the Docker host does not update the runtime in the image.

For an existing service, inspect the build pipeline, project properties, publish profiles, and deployed artifact. A file called Orders.Api.exe does not prove that the app is self-contained: framework-dependent publishing can also produce an executable app host. [2]

A newer SDK is not evidence of a patched process

This command answers a build-tool question:

dotnet --version

It reports the selected SDK version. A global.json can affect that selection. To inventory the runtimes visible to the invoked dotnet, use:

dotnet --list-runtimes

That inventory is specific to the installation and architecture being queried. An x64 invocation does not automatically establish what an x86 service uses. [4]

The distinction matters during incident response. Someone checking a developer SDK, an administrator's terminal, or a different installation path may be inspecting an environment that the production service never uses.

Record the service's launch command, account, architecture, deployment path, and environment. Then verify the process after the rollout.

Framework-dependent: update the right runtime, then restart

Framework-dependent apps normally select an installed patch within their compatible runtime family when they start. The selection can be affected by runtime configuration, launch options, and environment variables. Installing .NET 10 does not, by itself, migrate a .NET 8 application to .NET 10. [3]

For an ASP.NET Core service, check the applicable ASP.NET Core shared framework as well as the .NET runtime. Updating an unrelated runtime family is insufficient.

An explicit Windows x64, framework-dependent publish command might be:

dotnet publish ./src/Orders.Api/Orders.Api.csproj -c Release -f net10.0 -r win-x64 --self-contained false -o ./artifacts/fdd

This shows how to make the mode explicit. For a fix delivered entirely through the shared framework, republishing the application is normally unnecessary; update that framework and restart the application. Adapt the project path and target to your environment. [5]

After updating the hosting environment, restart or recycle the relevant application processes using your normal deployment procedure. A successful installer run does not establish that every already-running worker has loaded new runtime bits.

For IIS, distinguish the shared runtimes from the ASP.NET Core Module. The Hosting Bundle includes hosting components, and its installation options can omit runtime components. Check what was installed and follow Microsoft's restart guidance for that hosting setup. A self-contained IIS application still needs its own application runtime updated. [12]

Self-contained: the patch has to reach the published artifact

A self-contained app selects its runtime during publishing. It does not adopt a newer shared runtime just because one appeared on the server. [3]

Rebuild and republish using an updated toolchain and the appropriate fixed runtime packs. Review SDK selection and runtime-version overrides in the project, imported properties, and publish profile.

For a net10.0 project, this Windows x64 example explicitly requests the .NET runtime version from the October 25 update:

dotnet publish ./src/Orders.Api/Orders.Api.csproj -c Release -f net10.0 -r win-x64 --self-contained true -p:RuntimeFrameworkVersion=10.0.14 -o ./artifacts/scd

RuntimeFrameworkVersion specifies an exact .NET runtime version for self-contained publishing. Treat this dated value as an example: advance explicit pins during later updates. It does not independently establish that the bundled ASP.NET Core framework or other dependencies contain their applicable fixes. [6]

Publish into a fresh output directory, test the result, and deploy the complete replacement artifact. Reusing an old publish folder or copying only the main application DLL can leave you with a mixture of old and new files.

A pipeline can reproduce the old deployment if it reuses stale inputs. Review separate restore and build stages: --no-restore skips restore, and --no-build also implies --no-restore. Those options are appropriate when the earlier stages have already resolved and built the intended updated inputs. [5]

Keep the resolved runtime-pack versions and the resulting artifact hash with the build record, then match that artifact to the deployment.

Containers: refresh the image and replace the running instance

A typical .NET multi-stage build separates the SDK used to publish from the runtime image used in production. Inspect both references in the existing Dockerfile:

Stage Example image for a .NET 10 ASP.NET Core app What it contributes
Build mcr.microsoft.com/dotnet/sdk:10.0 The SDK and build environment
Final mcr.microsoft.com/dotnet/aspnet:10.0 Shared frameworks used by a framework-dependent app

These are example image references. Microsoft's tag policies distinguish floating release-line tags from patch-specific tags. Verify the selected image's OS, architecture, and contents. [8]

With suitable floating tags, request fresh base images during the application image build:

docker build --pull -t orders-api:2026-10-26 .

--pull checks for fresh versions of the referenced images. --no-cache controls reuse of build layers; it does not independently fetch a newer base image. If your Dockerfile pins an old digest or patch version, update that reference first. The same pinned digest still identifies the same image. [7]

The new image must then be pushed or distributed and deployed through your usual process. Restarting an existing container does not replace it with the newly built image.

For a self-contained app copied into a container, inspect the application artifact too. A fresh final-stage image cannot substitute for republishing the bundled runtime.

My suggested deployment record includes the source revision, build identity, base-image digests, and final deployed image digest. Check the running replicas against it, including workers and scheduled jobs. A rolling deployment is still incomplete while old replicas continue serving requests or processing work.

Single-file and Native AOT need separate attention

Single-file deployment describes packaging. It supports both framework-dependent and self-contained applications, so the number of files does not tell you how runtime patching works. Inspect the effective publishing settings. [9]

Native AOT produces a self-contained native application with runtime code included at publish time. A shared-runtime installation does not replace that compiled code. Rebuild and redeploy using the updated toolchain and applicable runtime inputs. [10]

Self-contained single-file and Native AOT applications can run without a shared .NET installation. A framework-dependent single-file app still needs a compatible shared runtime.

Ask the running application what it is using

For an ASP.NET Core app, a small startup log can provide useful process-level evidence. Add using System.Runtime.InteropServices; with the imports at the top of Program.cs. Place the following after creating app and before calling app.Run():

app.Logger.LogInformation(
    "Process {ProcessId} started on {RuntimeDescription}; architecture {Architecture}",
    Environment.ProcessId,
    RuntimeInformation.FrameworkDescription,
    RuntimeInformation.ProcessArchitecture);

FrameworkDescription identifies the executing .NET implementation and usually includes its version. Correlate this display value with the deployed build, host or container, and replica identity. The log is useful evidence, not a complete vulnerability assessment. [11]

This is evidence about the core runtime. It does not establish the patch state of the ASP.NET Core shared framework, the IIS module, NuGet dependencies, or operating-system libraries. Verify the component named in the advisory against its corresponding deployment evidence.

Likewise, a runtimeconfig.json describes runtime requirements and settings. For a framework-dependent app, its requested version is not necessarily the patch version selected when the process started. [3]

For images that include the CLI, an inside-container inventory can help:

docker exec orders-api dotnet --list-runtimes

Treat it as an inventory of that container's shared installation, not proof that a self-contained app uses it. Minimal and Native AOT images may have no dotnet command at all.

Close the patch task with application evidence

I would close a runtime patch task only after establishing four things:

  1. Applicability: identify the affected component, platform, and fixed release from the current advisory.
  2. Delivery: show that the relevant shared installation, application artifact, or container image contains the fix.
  3. Activation: confirm that the intended processes and replicas are running the updated deployment.
  4. Behavior: exercise the application's critical paths. Know whether a rollback would reintroduce the vulnerable component, and plan that contingency explicitly.

A server can be updated while an application remains behind. The useful completion record names the application, the deployed artifact, and the process using it.
