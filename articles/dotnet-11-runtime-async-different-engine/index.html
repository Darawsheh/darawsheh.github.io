The Same async/await, a Different Engine: Inside .NET 11 Runtime Async

How .NET 11 moves async machinery toward the JIT, why some Task allocations disappear, and how to test the opt-in preview safely.

By Islam Darawsheh November 9, 2026 12 min read

For more than a decade, C# developers have written async methods without having to manage callbacks or continuation state manually. The code reads almost like a synchronous method, even though its execution may stop at an await and resume later on another thread.

What changed in .NET 11 is not that programming model. It is who does the work of turning an async method into something the runtime can suspend and resume.

Traditionally, the C# compiler lowered each async method into a generated state machine. Runtime Async V2 moves much of that transformation into the runtime and JIT. That creates new opportunities to remove intermediate tasks, reduce generated code, and make live call stacks easier to inspect. It does not mean every async method becomes allocation-free or every workload becomes faster. [1][2]

Version context: As of November 9, 2026, .NET 11 is at RC2, with its official launch event scheduled to begin November 10. Runtime Async remains a preview feature for application code and must be explicitly enabled. The .NET 11 runtime libraries are already built with it. [1][6]

The machinery behind a familiar await

Consider a deliberately small method:

static async Task<int> ReadAsync(Task<int> pendingRead)
{
    int result = await pendingRead;
    return result;
}

With traditional compiler lowering, the source method is not emitted as an ordinary method containing a literal suspension instruction. The compiler creates an entry point and a state-machine type. That generated type has a MoveNext() method, fields for state that must survive an incomplete await, an awaiter, and an async method builder that manages completion and errors. The generated machinery implements IAsyncStateMachine.

This design has been refined for years. An already-completed operation can follow a fast path; an async call does not automatically allocate a fresh heap object for every state machine or every await. Still, the compiler has already committed to a particular representation before the JIT gets to optimize it. [2]

A simplified comparison is:

Traditional async (compiler-lowered)
C# async method
    -> generated state machine + MoveNext()
    -> builder, awaiter, and continuation handling
    -> runtime executes the generated code

.NET 11 Runtime Async (opt-in)
C# async method
    -> suspension-aware IL + async method metadata
    -> runtime/JIT handle suspension and resumption
    -> public Task/ValueTask contract remains intact

The difference matters most when one small async method awaits another, which awaits another—an ordinary pattern in application services, middleware, and libraries.

What the compiler now emits

With Runtime Async enabled, an eligible method is marked with the MethodImplOptions.Async metadata flag. Rather than emitting an IAsyncStateMachine implementation for that method, the compiler can emit compact IL that uses runtime-recognized helpers such as AsyncHelpers.Await<T>(). [2][3]

For this source method:

static async Task<int> CallerAsync() => await CalleeAsync();

The runtime-async IL has roughly this illustrative shape (not a verbatim disassembly):

.method ... Task<int> CallerAsync() cil managed async
{
    call Task<int> CalleeAsync()
    call int32 AsyncHelpers::Await<int32>(Task<int>)
    ret
}

The intriguing part is the apparent mismatch: the method advertises Task<int>, while its final ret consumes an int. That is valid under the proposed runtime-async calling convention, where the runtime manages the externally visible task boundary. The actual metadata, calling conventions, and helper signatures are described in the draft specification. [2][3]

There is a subtle detail here: the method's public signature may still be Task<int>, but the runtime can use a second, internal calling convention for a direct async call. Stephen Toub describes these as related method identities: the normal entry point preserves the task-returning API, while an AsyncCall variant can deliver a result directly or arrange a continuation. [2]

That is how the runtime can optimize this chain:

static async Task<int> AAsync() => await BAsync();
static async Task<int> BAsync() => await CAsync();
static async Task<int> CAsync()
{
    await Task.CompletedTask;
    return 42;
}

The completed await in CAsync keeps this path synchronous. The important pattern is the direct call followed immediately by an await.

In the traditional model, each method has its own lowered machinery and task-like completion boundary. Under Runtime Async, the JIT can recognize a direct call-and-await pattern and, where safe, connect the calls without materializing a separate intermediate Task<int> at every layer. When the deepest call finishes synchronously, the value can travel up the fused chain. When it suspends, the runtime maintains the continuation chain. The outer caller still receives the public Task<int> it expects. [2]

The task contract is not being removed. If your code needs to keep a task, pass it to Task.WhenAll, attach a continuation, or otherwise observe it as an object, the runtime cannot simply pretend that object does not exist. This optimization targets boundaries that are not observably required.

How to enable Runtime Async in .NET 11

Runtime Async is opt-in for application code. In a project targeting net11.0, the documented setting is:

<PropertyGroup>
  <Features>$(Features);runtime-async=on</Features>
</PropertyGroup>

For experiments, use a conditional MSBuild property so the same source can be compiled with the feature on or off:

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net11.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
    <Features Condition="'$(RuntimeAsync)' == 'true'">$(Features);runtime-async=on</Features>
  </PropertyGroup>
</Project>

Compile and run the same code in two configurations:

dotnet run -c Release --property:RuntimeAsync=false
dotnet run -c Release --property:RuntimeAsync=true

The custom RuntimeAsync property above only controls whether our project appends the documented compiler switch. It is not a built-in runtime environment variable. You do not need LangVersion=preview or EnablePreviewFeatures=true for this feature in net11.0. Earlier posts that recommend the old DOTNET_RuntimeAsync environment-variable switches are out of date. [1][2]

Experiment 1: inspect a live call stack

Put this in Program.cs:

using System.Diagnostics;

await EndpointAsync();

static async Task EndpointAsync()
{
    await Task.CompletedTask;
    await ServiceAsync();
}

static async Task ServiceAsync()
{
    await Task.CompletedTask;
    await RepositoryAsync();
}

static async Task RepositoryAsync()
{
    await Task.CompletedTask;
    Console.WriteLine(new StackTrace(fNeedFileInfo: true));
}

With traditional lowering, a live stack can expose infrastructure such as AsyncMethodBuilderCore.Start and repeated generated method frames. With Runtime Async, the live stack is generally closer to the source-level EndpointAsync -> ServiceAsync -> RepositoryAsync path. The exact frame count and names depend on build and inlining. Microsoft documents a comparable example with 13 frames without Runtime Async and 5 frames with it. Those are Microsoft's published results, not measurements taken for this article. [1]

There is an important distinction: this example deliberately uses completed awaits, so the methods remain on the physical call stack during the sample. Once an operation actually suspends, the thread stack unwinds. A later physical stack trace is not automatically a complete logical history of the asynchronous operation. That requires async-aware diagnostic tooling. Also, exception stack traces already have cleanup that makes them much more readable than raw live stacks, so do not expect the same dramatic difference in catch (Exception ex) output. [1][2]

Experiment 2: benchmark the synchronous and suspended paths

To test allocations and time, create a separate .NET 11 console benchmark project using the conditional .csproj setting above, then install BenchmarkDotNet:

dotnet add package BenchmarkDotNet

Replace its Program.cs with:

using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

BenchmarkRunner.Run<AsyncChainBenchmarks>();

[MemoryDiagnoser]
[InProcess]
public class AsyncChainBenchmarks
{
    private static readonly Task<int> Completed = Task.FromResult(42);

    [Benchmark]
    public Task<int> CompletedPath() => OuterAsync(shouldYield: false);

    [Benchmark]
    public Task<int> SuspendedPath() => OuterAsync(shouldYield: true);

    private static async Task<int> OuterAsync(bool shouldYield)
        => await MiddleAsync(shouldYield);

    private static async Task<int> MiddleAsync(bool shouldYield)
        => await InnerAsync(shouldYield);

    private static async Task<int> InnerAsync(bool shouldYield)
    {
        if (shouldYield)
            await Task.Yield();

        return await Completed;
    }
}

Build and run each configuration explicitly:

# Traditional compiler lowering
dotnet build -c Release -p:RuntimeAsync=false --no-incremental
dotnet run -c Release --no-build

# Runtime Async lowering
dotnet build -c Release -p:RuntimeAsync=true --no-incremental
dotnet run -c Release --no-build

[InProcess] runs the benchmarks using the already-compiled benchmark assembly. This avoids BenchmarkDotNet's default out-of-process toolchain potentially generating a new build without the custom feature switch. In-process execution has different isolation and timing tradeoffs; do not directly compare its absolute results with Microsoft's published out-of-process microbenchmarks. Retain the reports from both runs. [7]

CompletedPath explores a chain whose awaited task is already completed. SuspendedPath introduces a real asynchronous yield. BenchmarkDotNet handles repeated execution and reports allocations, but the results will depend on the SDK, runtime build, hardware, JIT warm-up, and test conditions. The snippets describe experiments for readers to reproduce; they have not been compiled or run as part of preparing this article.

Keep the full runtime version constant between the two builds. Comparing .NET 10 against .NET 11 would also include many unrelated runtime improvements and would not isolate the effect of the lowering strategy.

What published measurements actually show

Stephen Toub published a controlled .NET 11 microbenchmark that compares two-layer async chains using classic compiler lowering versus Runtime Async in the same runtime. His benchmark used an experimental, compiler-recognized per-method opt-out to keep the comparison focused. Selected results: [2]

ScenarioTraditional loweringRuntime AsyncAllocated, traditionalAllocated, Runtime Async
Two-layer completed chain21.221 ns6.151 ns144 B0 B
Two-layer yielding chain254.139 ns116.927 ns248 B168 B

These are author-reported microbenchmark results for that exact setup, not results from the preceding three-layer example and not general application-level speedup estimates. The zero-byte entry is an allocation measurement for one narrowly defined benchmark operation, not a promise that a real HTTP request or database operation will allocate nothing.

There is also a counterexample to blanket performance claims: in Toub's exception-handling benchmark, one shallow yielding case measured 6.308 μs with classic lowering versus 8.211 μs with Runtime Async. Deeper chains performed substantially better with Runtime Async. That variation is exactly why a preview runtime feature needs workload-specific measurement. [2]

The same investigation reports a small compiled-assembly probe—ten async methods—shrinking from 10,752 bytes to 5,632 bytes with Runtime Async. Again, that is one demonstration, not a universal 48% reduction in application size. [2]

Not just fewer tasks: optimizations across the execution path

Runtime Async gives the JIT control over suspension points and allows optimizations that were harder once the compiler had already expanded each method into a state machine. The .NET 11 work includes tail merging of suspension points, tiered compilation for async variants, continuation reuse, and recognition of common Task and ValueTask factories. ReadyToRun and NativeAOT support also landed during the preview cycle. [1][4]

There is a related but distinct .NET 11 improvement involving ExecutionContext. A continuation can skip capture-and-restore work when there is no ambient state to restore. AsyncLocal<T> values still need to flow correctly when present. This optimization also benefits traditional Task/ValueTask paths; it should not be counted as a Runtime-Async-only gain. [1]

Nor should it be confused with ConfigureAwait(false). ConfigureAwait(false) affects how a captured synchronization context or scheduler is used for continuation scheduling; it does not switch off ExecutionContext flow or erase AsyncLocal<T> values. [5]

Compatibility, limits, and an important API-design reminder

The intention is behavioral compatibility: existing await, exceptions, cancellation, and ConfigureAwait semantics should continue to work, whether the method was lowered by the compiler or by the runtime. Older libraries and newly compiled runtime-async code can interoperate via adapters at their boundaries. A semantic difference would be a bug, not a new behavior applications are supposed to depend on. [2][3]

The current feature targets methods returning Task, Task<T>, ValueTask, or ValueTask<T>. async void, async iterators, and custom task-like builder types still use traditional compiler lowering. Therefore, enabling the feature does not remove every generated async state machine from an arbitrary application. [2]

It also does not make ValueTask<T> obsolete. The choice between Task<T> and ValueTask<T> remains a question of API contracts, expected synchronous completion rates, caller behavior, and measurement—not simply which type looks lighter in a benchmark.

The feature remains opt-in and preview for application code in .NET 11. Stephen Toub has expressed hope that Runtime Async could become enabled by default in .NET 12; that is an expectation, not a shipping commitment. [1][2]

How I would evaluate it in a real ASP.NET Core service

Begin with one representative, async-heavy service rather than enabling a preview switch across every repository. Compare two builds of the same .NET 11 version, one with Runtime Async disabled and one enabled. Keep request mix, dependency versions, caching, connection pools, deployment settings, and load-generator behavior constant.

Record p50/p95/p99 request latency, throughput, allocated bytes and Gen 0/1/2 collections, CPU use, assembly size, and behavior under concurrency. Include a cold-start test if startup matters. Test successful calls, cancellation, exception paths, and workflows that rely on AsyncLocal<T> or ConfigureAwait behavior. Confirm that exception handling and returned results remain identical.

A microbenchmark helps identify a mechanism. A load test shows whether that mechanism matters when networking, databases, serialization, and other work dominate an endpoint. A small canary is useful only after compatibility and operational tests pass—and an opt-in preview should still be treated as a deliberate production risk decision.

The real takeaway

The valuable change in .NET 11 is that the compiler no longer has to decide the entire execution strategy for every eligible async method before the runtime sees it. The JIT can recognize direct async chains and avoid some of the intermediate machinery that was previously baked into the compiled representation.

For developers, the advice is refreshingly unchanged: write readable async code, pass cancellation where appropriate, keep Task as the ordinary default, and do not flatten clean abstractions solely to avoid hypothetical async overhead. If you want to explore the new engine, enable it in a controlled .NET 11 experiment and measure the workload that matters to you.

The async/await you write is the same. The implementation beneath it is becoming more capable.
