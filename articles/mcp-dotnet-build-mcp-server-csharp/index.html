MCP in .NET: What It Actually Solves and How to Build an MCP Server in C#

MCP gives AI hosts a standard way to discover and use external capabilities. The useful question for .NET teams is not whether MCP is popular—it is where the protocol belongs in a real architecture, how to expose tools safely, and when a normal API is still the better choice.

By Islam Darawsheh August 31, 2026 10 min read

AI models are increasingly good at deciding what should happen next. The harder engineering problem is giving them a controlled, reusable way to interact with the systems that can actually do the work.

An assistant may need to search customer records, inspect an order, read internal documentation, query a Git repository, or trigger an existing business operation. None of those capabilities are difficult to expose once. The problem appears when every AI host, IDE, agent, and model integration needs its own custom adapter.

That is the problem the Model Context Protocol (MCP) is trying to solve.

The official MCP C# SDK reached v2.0 on July 28, 2026, implementing the 2026-07-28 protocol revision. That revision made MCP over HTTP stateless by default, standardized HTTP routing metadata, and introduced Multi Round-Trip Requests for interactive operations without requiring a long-lived session.

The important distinction:

MCP is not a replacement for your domain, application services, database, or REST API. It is an AI-facing integration boundary that can sit on top of capabilities you already have.

What MCP actually solves

Without a common protocol, an organization can quickly end up with an integration matrix like this:

AI Assistant A
   +-- CRM adapter
   +-- Orders adapter
   +-- Docs adapter

AI Assistant B
   +-- CRM adapter
   +-- Orders adapter
   +-- Docs adapter

The APIs underneath may already exist. The duplicated work is teaching each AI host what capabilities are available, how arguments are described, how operations are invoked, how context is exposed, and how results are returned.

MCP standardizes that boundary:

AI Host
   |
MCP Client
   |
MCP Protocol
   |
MCP Server
   |
Application Services
   |
Existing Systems

The host owns the conversation and model interaction. The MCP server exposes a focused set of capabilities. The business application underneath does not suddenly become an AI application; it simply gains another adapter.

Tools and resources are the concepts most .NET teams need first

A tool is an operation an MCP client can invoke. Examples include get_order_status, search_customers, or create_support_ticket. A resource exposes information that can be read as context, such as a policy document, product documentation, or a repository file.

Tool     = perform or calculate something
Resource = provide information

MCP also supports prompts and extensions, but tools and resources are enough to understand the architecture before adding more protocol surface.

Build an MCP server with ASP.NET Core

For an HTTP server, the official SDK provides the ModelContextProtocol.AspNetCore package.

dotnet new web -n Company.McpServer
cd Company.McpServer
dotnet add package ModelContextProtocol.AspNetCore

A minimal server can be configured like this:

using ModelContextProtocol.AspNetCore;
using ModelContextProtocol.Server;

var builder = WebApplication.CreateBuilder(args);

builder.Services
    .AddMcpServer()
    .WithHttpTransport(options =>
    {
        options.SessionMode = HttpServerSessionMode.Stateless;
    })
    .WithToolsFromAssembly();

var app = builder.Build();
app.MapMcp();
app.Run();

Stateless HTTP is the default in the v2 SDK, so setting it explicitly is mainly useful when you want the deployment assumption to be obvious in code.

Now expose a simple tool:

using ModelContextProtocol.Server;
using System.ComponentModel;

[McpServerToolType]
public static class OrderTools
{
    [McpServerTool]
    [Description("Returns the current status of an order.")]
    public static string GetOrderStatus(
        [Description("The order identifier")] int orderId)
    {
        return $"Order {orderId} is currently Processing.";
    }
}

WithToolsFromAssembly() discovers classes marked with [McpServerToolType] and registers methods marked with [McpServerTool]. The SDK generates the JSON schema for tool parameters from the .NET method signature and descriptions.

The MCP tool should call your application layer—not your database directly

The previous tool is useful as a demo, but real systems already have business rules and application services. MCP should normally sit above them.

REST API  -----\
                \
SignalR ---------> Application Layer --> Domain
                /
MCP Server -----/

I would avoid an MCP tool that talks directly to DbContext, and I would definitely avoid generic tools such as execute_sql. A better boundary is a thin MCP adapter over an existing use case.

public interface IOrderQueryService
{
    Task<OrderStatusDto?> GetStatusAsync(
        int orderId,
        CancellationToken cancellationToken);
}

[McpServerToolType]
public static class OrderTools
{
    [McpServerTool(Name = "get_order_status")]
    [Description("Gets the current status of an order.")]
    public static async Task<object> GetOrderStatus(
        IOrderQueryService orders,
        [Description("The order identifier")] int orderId,
        CancellationToken cancellationToken)
    {
        var order = await orders.GetStatusAsync(
            orderId,
            cancellationToken);

        return order is null
            ? new { found = false, orderId }
            : new
            {
                found = true,
                order.Id,
                order.Status,
                order.LastUpdated
            };
    }
}

The SDK can resolve registered services for tool invocation, while the tool remains responsible for validating untrusted arguments and enforcing the application's rules.

This is also where tool design starts to differ from simply mirroring your REST endpoints. An API contract is designed for software clients. An MCP tool is selected inside an AI-driven workflow. Sometimes a task-oriented tool such as get_customer_order_summary is safer and more useful than exposing ten low-level CRUD operations.

What MCP C# SDK 2.0 changes for backend architecture

The most interesting v2 changes are not new C# attributes. They make MCP fit normal HTTP infrastructure much better.

Stateless HTTP is now the default

Earlier Streamable HTTP flows commonly relied on an initialization handshake and an MCP session identifier. Horizontal deployments then needed to preserve that transport state through sticky routing or shared session storage.

The 2026-07-28 protocol revision makes requests self-contained, so any instance can handle a normal request:

               +-- MCP Server 1
               |
Load Balancer -+-- MCP Server 2
               |
               +-- MCP Server 3

That is a major simplification for containers, Kubernetes, serverless workloads, reverse proxies, and horizontally scaled ASP.NET Core applications.

Stateless transport does not mean your business process cannot have state. If one operation returns a workflowId, browserId, or another handle, later calls can pass that identifier explicitly—the same pattern we already use in ordinary APIs.

Gateways can understand MCP traffic using HTTP metadata

The new protocol standardizes headers such as Mcp-Method and Mcp-Name. Tool parameters can also be intentionally mirrored into Mcp-Param-* headers.

That means a gateway, load balancer, WAF, or observability platform can make routing and policy decisions without parsing the JSON-RPC request body. For enterprise deployments, that is much more important than it sounds: MCP can participate in infrastructure patterns teams already know how to operate.

Multi Round-Trip Requests support interactive tools without persistent sessions

Some operations need more information before they can complete. Imagine a tool asked to close a support ticket, but the server requires a reason or explicit confirmation.

Client -- call tool --> Server
Client <-- input_required -- Server

Client asks user or model

Client -- tool + response --> Server
Client <-- completed result -- Server

Multi Round-Trip Requests (MRTR) let the server return an input_required result containing the input it needs and opaque request state. The client gathers the answer and calls the tool again. The interaction can continue over normal request/response HTTP rather than keeping a bidirectional session open.

That is particularly useful for sensitive write operations where confirmation is part of the workflow.

MCP does not replace REST—or provider function calling

If your mobile app needs CRUD operations or Service A needs to call Service B, REST, gRPC, or messaging are usually still the natural choice.

REST / gRPC / Messaging
= application-to-application integration

MCP
= discoverable capability integration for AI hosts

Function calling is related but narrower. Provider-specific function calling answers, "How can this model call the functions I give it?" MCP defines a broader interoperability contract for discovering capabilities, describing tools and resources, transporting requests, and integrating clients and servers.

In many systems the right architecture is coexistence, not replacement:

Web / Mobile ----> REST API ----\
                                \
                                 > Application Layer
                                /
AI Hosts -------> MCP Server --/

Security: treat every MCP tool as an API surface

This is the part I would design before exposing write-capable tools.

A generic tool such as this is flexible:

[McpServerTool]
public Task ExecuteSql(string sql)

It is also an unnecessarily dangerous boundary for most business applications.

Prefer narrow capabilities:

execute_sql(query)
    X
get_customer_balance(customerId)
    ✓

run_command(command)
    X
restart_test_worker(workerId)
    ✓

Narrow tools are easier to authorize, validate, audit, test, rate-limit, and reason about. Tool descriptions help the model understand intent, but descriptions are not security controls.

Authentication, authorization, validation, business rules, database constraints, audit logging, and idempotency still belong on the server. The official SDK documentation also warns HTTP server developers to validate expected host names to reduce DNS rebinding risk and to configure normal web controls such as CORS carefully.

For operations such as cancelling an order, approving a payment, resetting a password, or deploying software, I would also consider explicit confirmation and MRTR rather than blindly executing every generated tool call.

Where MCP belongs in Clean Architecture

If the application already follows a layered or Clean Architecture style, MCP is best treated as another delivery adapter.

Company.Domain
Company.Application
Company.Infrastructure
Company.Api
Company.Mcp

The dependency direction should remain familiar:

REST API -----\
              \
               > Application --> Domain
              /
MCP Server --/

Infrastructure implements outward-facing concerns

The MCP project may know about ModelContextProtocol, ASP.NET Core, transport, authentication, and MCP-specific schemas. The domain should know nothing about MCP.

If domain rules begin checking whether a request "came from MCP," that is usually a sign the adapter boundary has leaked into business logic.

When should you actually use MCP?

I would seriously consider MCP when a capability should be discoverable and reusable across multiple AI hosts, when you are building internal AI infrastructure over existing enterprise systems, or when you are exposing developer tooling such as repository analysis, diagnostics, testing, build systems, documentation, or issue tracking.

I would probably not add MCP when one backend simply needs to call another service, when a mobile application needs ordinary CRUD endpoints, or when one internal model needs one hardcoded function and there is no real interoperability requirement.

The useful decision rule is simple:

Do not ask, "Can this become an MCP server?"

Ask whether this capability needs to be discoverable and interoperable across AI hosts. If the answer is no, a normal API may be the cleaner design.

Final thoughts

MCP is sometimes described as "USB-C for AI." The analogy explains standardization, but it can hide the more important architectural idea.

We already knew how to make an LLM call a function. MCP is interesting because it creates a standard capability boundary between AI hosts and the systems they need to use.

AI Host
   |
MCP Client
   |
MCP Server
   |
Application Layer
   |
Existing Systems

With the official C# SDK at v2.0, ASP.NET Core integration, stateless HTTP by default, standardized routing metadata, and Multi Round-Trip Requests, MCP now fits much more naturally into normal .NET web architecture.

That does not mean every API should become MCP.

Use MCP when you need an AI capability protocol. Use an API when you need an API.

Knowing the difference is more valuable than adopting either technology because it is fashionable.
